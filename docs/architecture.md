# Forge — Architecture Contract

This file is the binding contract between the three components. Any change to a wire format or command name happens HERE first, then in code.

## Components and ports

| Component | Location | Runs | Listens |
|---|---|---|---|
| Blender add-on (`forge`) | `addon/forge/` | inside Blender | TCP `127.0.0.1:9876` |
| Geometry service | `service/` | standalone Python (Build123d) | HTTP `127.0.0.1:8765` |
| MCP server | `mcp/` | spawned by Claude Code (stdio MCP) | — (client of both) |

Data flow:

- Claude Code → MCP server → Blender socket (scene ops, mesh loading, common ops like symmetrize).
- Claude Code → MCP server → geometry service (generate/export parametric parts).
- Blender panel sliders → geometry service directly (HTTP via urllib, no third-party deps inside Blender) → mesh reloaded in place.

## Blender socket protocol (TCP 9876)

Newline-delimited JSON, UTF-8. One request object per line, one response object per line.

Request: `{"id": "<optional>", "type": "<command>", "params": { ... }}`
Response: `{"id": "<echoed>", "status": "success" | "error", "result": <object|null>, "message": "<human-readable, set on error>"}`

The socket server runs on a background thread; **all bpy work executes on the main thread via a `bpy.app.timers` command queue**. Errors must be caught and returned as `status: "error"`, never crash the server.

Units: Blender scene units are meters; geometry service works in millimeters. `load_mesh` receives **millimeter** coordinates and the add-on scales by 0.001 on import (objects keep scale 1.0; vertices are scaled).

## Geometry service HTTP API (8765)

JSON request/response bodies.

- `GET /health` → `{"status": "ok", "build123d": "<version>"}`
- `POST /parse_params` `{"script": "<source>"}` → `{"params": <PARAMS schema, resolved>}` (no geometry built)
- `POST /generate` `{"script": "<source>", "overrides": {"<param>": value, ...}}` → `{"params": <schema>, "mesh": {"vertices": [[x,y,z]mm,...], "faces": [[i,...],...]}, "stats": {"vertex_count", "face_count", "bounding_box_mm": [x,y,z], "watertight": bool}}`
- `POST /export` `{"script", "overrides", "format": "stl"|"step"|"3mf", "path": "<absolute output path>"}` → `{"path": str}`

Errors: HTTP 400 with `{"error": "<message>", "traceback": "<optional>"}` for script/param failures; 500 for service bugs.

### Finishing-chain order and LOD budgets (2026-09-13, research-verified) — implemented

**The canonical order is `repair → retopo → UV unwrap → bake high→low → tangents → LOD`, and `rigforge_retopo` now runs it.** The previous order built LODs from an un-unwrapped retopo and baked before unwrapping, which made both steps worthless without erroring. Binding:

- `rigforge_retopo` gains **`unwrap`** (default `true`): stage 5 is now `rigforge_auto_uv`'s own code on LOD0, between the tag transfer and the bake. Result gains `uv` (the auto_uv report) and `unwrapped`.
- **A bake into a mesh that has never really been unwrapped is refused, in a sentence.** `bake_normals=true` with `unwrap=false` is a `ForgeError`; `bake_normals()` itself refuses a mesh carrying no `forge_uv_unwrapped` custom property (written only by a real unwrap) and no longer invents a filler UV layer. The filler layer is exactly what the next unwrap replaces, so a bake into it silently self-invalidates.
- **LODs are cut from the unwrapped LOD0**, never from the level above, so every level shares LOD0's atlas and one baked map serves the chain.
- **LOD targets are triangle budgets, not `0.5 ** level` ratios.** Game budgets `{"desktop": 50000, "mobile": 10000}`; the default chain starts at `min(LOD0 triangles, platform budget)` and takes a quarter per level (floor 64); override with **`lod_budgets": [int, ...]`**. Result gains `lod_reports` (per level: `budget`, `ratio`, `triangles`, `face_count`, `within_budget`, measured `error`/`error_mean`/`error_relative`, `visibility_begin`, `uv_layer`), `lod_budgets`, `lod_budget_source` and `budget` (`platform`, `lod0`, `lod0_faces`, `lod0_triangles`, `unit: "triangles"`, `within_budget`). A missed budget is a warning, never silent.
- `visibility_begin` is `error × 704 / error_px` — the distance at which a level's measured error falls under one pixel at 1080p/75° FOV. It is stored on each LOD object as `forge_lod` and is what the Godot export turns into visibility ranges.
- **Known limitation (documented, not fixed here):** Blender's Decimate Collapse is a position-only quadric with no UV term, so UV distortion under decimation is unbounded. Its vertex group is a *hard lock, not a soft cost* (measured on Blender 5.0.1: any membership prevents collapse regardless of weight or `vertex_group_factor`), so **`protect_seams` defaults to false** — locking an unwrapped character's seams floors the reduction far above any budget. Measured atlas drift on the test character is median 0.0003 / 0.0008 at LOD1 / LOD2. The real fix is a meshoptimizer `simplifyWithAttributes` ctypes binding — implemented in the next section; this paragraph now describes the **fallback** path.

### meshoptimizer simplifyWithAttributes — UV-preserving LODs (2026-09-15, research-verified) — implemented, DLL build blocked

The queued lane below, built. `native/meshopt/` vendors meshoptimizer's MIT library sources pinned at **`3d62f11a3cea144593700a167aff14410fa084e2`** (2026-09-12; the floor is `ce73e457`, 2026-09-09, "Stabilize many experimental APIs" — `meshopt_SimplifyPermissive` and `meshopt_generateTangents` are experimental or absent before it and the `v1.2` tag predates both). The stale PyPI binding is not used. `native/meshopt/build.ps1` probes `cl.exe` (via vswhere) → `clang++` → `cmake` → `zig c++` and compiles `meshoptimizer/*.cpp` into `meshoptimizer.dll` in one command with `MESHOPTIMIZER_API=__declspec(dllexport)` — the library is dependency-free C++ with a C interface, so there is no configure step and no cmake ceremony.

- **`addon/forge/tools/meshopt.py`** is the binding: ctypes over `meshopt_simplifyWithAttributes` (+ `simplify`, `generateVertexRemap`/`Multi`, `remapIndexBuffer`/`VertexBuffer`), no numpy (`array` buffers, because `foreach_get` yields flat lists), no `bpy`. `simplify_lod(vertices, indices, uvs, normals, target_index_count, target_error, weights) -> (indices, result_error)`.
- **The result indexes the original vertex buffer**, so a surviving vertex keeps its original position *and UV, bit for bit*. LODs therefore **carry** LOD0's atlas rather than resampling it, and one baked map serves the chain exactly.
- **`protect_seams` becomes unnecessary** and is ignored on this path: a seam is an attribute discontinuity the quadric prices, not a border that has to be locked, so none of the budget is spent protecting it. The flag remains for the Decimate fallback.
- Three silent failures encoded: **unwelded input no-ops** (the simplifier hashes raw position float bits — UV wedges stitch, a triangle soup has no shared edges and collapses nothing while reporting success, so `weld_report` refuses it by name *before* the DLL is even loaded); **`result_error` is not a success signal** (it describes what was collapsed; a run that did nothing reports 0.0 — the achieved index count is always asserted, `require_target=True` raises `MeshoptTargetMissed`); **gltfpack's UV weight is 0.0** (`gltf/mesh.cpp: simplifyAttributes` weights texcoords `update ? 1.f : 0.f`, so copying it verbatim yields a UV-blind simplifier). Weights here: normals 1.0 per scalar, UVs from the mesh's reciprocal UV density × priority, clamped to the researched 10–100 band. Flags otherwise follow gltfpack: `Permissive | Prune`.
- **`lod_reports[].simplifier`** (and `result.simplifier`, and each LOD object's `forge_lod`) is `"meshopt <commit>"` or `"blender-decimate (meshopt unavailable: <reason>)"` — a report that named only Decimate would hide the difference between "the lane is not wired up" and "nobody built the DLL". A mid-flight meshopt failure degrades the same way, as `"(meshopt failed: ...)"`.
- **Blocker: no C++ toolchain on this machine** (2026-09-15 — no Visual Studio/Build Tools or vswhere, no LLVM, no cmake, no zig, no mingw; the only WSL distribution is Docker Desktop's utility VM, and `winget` is absent). `build.ps1` writes `meshopt_build.json` with `"status": "blocked"` and that reason, and the pipeline runs the Decimate fallback quoting it. Installing any one of VS Build Tools / LLVM / zig unblocks the lane with **no code change**; `native/meshopt/README.md` carries the table. Deploy must copy the DLL to `<add-on>/forge/lib/`, since an installed extension cannot see the checkout (`FORGE_MESHOPT_DLL` overrides).
- Tests: `addon/tests/headless_meshopt.py` (27 checks green with no DLL, 5 skipping with the reason) — including **binding arities checked against the vendored `meshoptimizer.h`**, which is the one binding bug a machine without the library can still catch. `headless_rigforge.py` gains the report-field and fallback-reason assertions plus a **round-trip test of the mesh bridge** (`_mesh_to_meshopt_buffers` → `_rebuild_mesh_from_indices` must reproduce the mesh triangle-for-triangle with bit-identical UVs and its tags intact), which exercises the risky Blender half of the path without the simplifier.

### Deterministic retopo route — `method` on `rigforge_retopo` (2026-09-19, measured) — implemented

The determinism law meets Blender's Quadriflow: on byte-identical input (the pinned 26 674-vertex voxel-remeshed sculpt, `seed=0`, symmetry off) fresh processes return identical topology but different vertex positions — 225 of 3 574 vertices up to **45.8 mm** apart. Measured before concluding: `OMP_NUM_THREADS=1` does **not** still it (the race is not OpenMP's); a whole-process **`blender --threads 1` launch does** (7/7 byte-identical digests) — the solve rides Blender's task scheduler, whose size is a launch flag no running session or per-call setting can change. So a per-call deterministic Quadriflow does not exist on this build; the product's answer is a route choice:

- `rigforge_retopo` gains **`method`**: `"auto"` (default — Quadriflow with the collapse-decimate fallback, exactly the old behaviour, output varies run to run), `"quad"` (Quadriflow only, refuses rather than falling back), `"decimate"` (the collapse decimate straight to the target — a pure function of its input, byte-identical across processes). Result gains `method` (requested), keeps `quad_method` (what ran: `quadriflow` / `decimate` / `decimate_fallback`), and gains **`deterministic`** (true on either decimate route). Panel: a Method dropdown on the Retopo panel with a "varies run to run" note on the Quadriflow choices.
- Anything that must replay exactly — the shared test character, flows that pin digests — takes `method="decimate"`. `headless_rigik.build_character` now asks for it by name instead of monkeypatching `_quad_remesh`, and `CHARACTER_DIGEST` (unchanged) stays the cross-process pin; `headless_rigforge.test_retopo_deterministic_route` gates the route with a two-run digest comparison (coordinates + polygons + weights) and asserts an unknown `method` is refused by name.

### IK, planted feet and the foot-slide gate (2026-09-17, measured) — implemented

The owner's audit — *"are we actually doing best practices on rigging and animation like inverse kinematics for legs?"* — turned up a walk keyed on `thigh_fk`/`shin_fk`. Three answers, all measured on the installed Blender 5.0.1, all additive:

- **The builder is Rigify and the IK was already there.** The 29 bones an audit sees are the **metarig** (`basic_human`, 29 bones — what `rigforge_metarig` places and fits). Rigify's generate turns them into a **222-bone control rig, 35 of them deform**, carrying `foot_ik`/`hand_ik` targets, `thigh_ik_target`/`upper_arm_ik_target` poles, the classic three-pivot foot roll (`foot_heel_ik` / `foot_spin_ik` / `toe_ik`), and a per-limb `IK_FK` blend on `thigh_parent.*` / `upper_arm_parent.*` driving real `IK` constraints of chain length 2. A custom lightweight skeleton was considered and **rejected**: it would have reproduced all of that, worse.
- **Forge's own tooling was switching it off.** `rigforge_keyframe`/`rigforge_retarget` called `set_fk` on the *whole rig* whenever any FK bone was keyed, so keying one arm took both legs off IK — silently. `fk_switch: "auto"` is now scoped to the limbs actually being keyed (`fk_limbs` in the result); `fk_switch: true` still switches everything, because a full-body mocap bake wants that.
- **The convention is defaulted and reported.** `rigforge_generate_rig` leaves every rig **legs IK, arms FK**, poles enabled, and reports it in a new `ik` block. Pole targets are not cosmetic: with Rigify's default `pole_vector` off, moving the pole bone changes the knee by **0.0 mm**.

| `animation_check` | `{"rig"?, "action"?, "mode"?: "auto"\|"planted"\|"in_place", "frame_step"?, "contact_band"?: 0.2, "min_stance_frames"?: 3, "feet"?: [bones]}` — the **foot-slide metric** | `{"mode", "mode_reason", "feet": [{bone, steps: [{frames, drift_mm, lift_mm, verdict}], worst_drift_mm}], "worst_step", "worst_drift_mm", "gate", "thresholds", "threshold_tier", "says", "pose_restored"}` |

**The metric, defined.** The **ball of the foot** (`DEF-toe.<side>` head, else `DEF-foot.<side>` tail) tracked in world space every frame — not the ankle, because a correct heel-off rolls the foot over the ball and the ankle *should* travel (measured: rolling the heel control 25° moves the ball and toe by 0.0 mm). A **stance phase** is a run of ≥3 frames whose ball sits within 20% of its own vertical range of its lowest point, with leading/trailing samples trimmed when they exceed 3× the run's median speed (the strike arriving, the toe leaving). **Drift** is the *diameter* of that run's horizontal position cloud in millimetres — a diameter, not a distance from the first sample, so a foot that slides out and back cannot read zero. `planted` expects zero; `in_place` first removes **one** shared velocity pooled over every stance sample of both feet, because a treadmill clip's feet must run backwards and only the *variation* is a fault; `auto` chooses by whether the body travelled. Bands (**heuristic tier**, uncalibrated, always quoted next to the measurement): ≤5 mm pass, ≤20 mm attention, above that fail.

**It proves itself both ways**, on one rig and one 32-frame cycle: `rigforge_walk` travelling **1.1 mm**, the same cycle in place **1.0 mm**, and the same walk keyed on `thigh_fk`/`shin_fk` **189 mm**. A 170× separation. Exported, baked and re-imported through the `.glb`, the IK walk still measures **4.3 mm**.

**Export is unaffected and now pinned.** `rigforge_export_godot` already baked with `nla.bake(visual_keying=True)` onto the deform rig and passed `export_force_sampling=True` — Godot needs baked bone transforms, not IK constraints. Tests assert both settings, that the installed exporter really carries `export_force_sampling` (rather than `op_kwargs` silently dropping it), that the walk's source action keys no deform bone at all, and that every animated node in the `.glb` is a `DEF-` bone or `root`. ### Corrective shape keys — the collapsed knee (2026-09-17, measured) — implemented

`rig_check` on a live character measured **40-50% volume loss at the knees and elbows at 90 degrees of flex**. The first fix tried was the obvious one and it is recorded here because it **failed**: a genuine edge-loop density pass around the joints moved the number from **50.3% to 51.1%** — nothing, inside the noise. That is not a bad retopology pass. Linear-blend skinning computes a posed vertex as a weighted average of *rigid transforms*, and the average of two rotations is a matrix shorter than either; at 90 degrees the shrink is the collapse, and it happens per vertex however many vertices there are. Adding loops adds samples of a function that is wrong at every sample. The fix every AAA pipeline uses is a **corrective shape key driven by bend angle** (a JCM / PSD), and it is now a command. Additive; no MCP mirror (same `mcp/` lane as `rig_check`).

| type | params | result |
|---|---|---|
| `rigforge_correctives` | `{"rig"?, "mesh"?, "action"?: "author"\|"report"\|"clear", "joints"?: ["knee.L", ...], "angle_samples"?: [0.5, 1.0] fractions of that joint's own extreme (or `{"flex_deg": 90}`), "strength"?: 0-1, "smooth"?: 0-1, "weight_floor"?, "verify"?}` — `joints` omitted = **the harness's own worst set** (`rig_check` at full flex, every joint whose volume verdict is not `ok`), and a rig where none fails is a refusal quoting the worst measurement, not invented work | `{"shape_keys", "joints": [{joint, driver_bones, driver_rest_angle_deg, skin_residual_mm, keys: [{name, flex_deg, vertices_moved, max_push_mm, worst_pinch_mm, driver_ramp, volume_loss_before_pct, volume_loss_after_pct}]}], "table", "gate_before", "gate_after", "rest_space", "says", "pose_restored"}` |

**The measurement.** Each vertex in the joint's neighbourhood (`rigcheck.JointProbe`'s own region, widened to the whole parent/child blend band so the correction tapers instead of stepping) gets a **radius**: its distance to the limb's two-segment skeleton — parent bone head, joint, child bone tail — taken at rest against the rest skeleton and again at the pose against the posed one. The shortfall is the pinch. Rotation-invariant by construction: a bent limb may *move*, it may not get *thinner*. The push is that pinch back out along the axis it was lost on, masked by `min(1, 2*sqrt(w_parent * w_child))` (zero where a vertex belongs to one bone alone, peak where the two are averaged — which is where linear blending does its damage) and Laplacian-smoothed over the mesh's edges with `silhouette._smooth_field`. Nothing sculpted, nothing eyeballed. The obvious alternative — push along the posed surface normal — was **implemented and measured worse**: 29.7% became **39.4%** where radial gives 13.6%, because the magnitude is measured as a loss of distance to the skeleton and in the crease of a fold the two facing walls' normals point at each other, so the correction closes the fold. It was removed rather than left as a knob, and a `direction` parameter is refused with that number in the sentence.

**The rest-space math.** A shape key is a rest-pose offset that the armature then deforms, so a posed-space delta is not the delta to store. With `p = M r`, `M = (Σ w)⁻¹ Σ w · (P_b A_b⁻¹)` conjugated into the mesh's own space exactly as the armature modifier does it, wanting `p + d` gives `Δr = L⁻¹ d` where `L` is `M`'s 3x3 linear part (the translation cancels between the two sides, so the pull-back is a per-vertex linear solve, not an inverse transform of a point). `Δr` is added to the **Basis key's** coordinates, not `mesh.vertices` — a shape-keyed mesh is evaluated key-mix-first and the raw vertices are not what gets deformed. The skinning model is **checked against the depsgraph** at the same pose and the worst disagreement ships as `skin_residual_mm` (0.0001 mm on the test limb); a large residual means something other than plain vertex-group skinning is at work and the run says so.

**The driver is a `ROTATION_DIFF` between the two bones that span the joint**, chosen from `(DEF-parent, DEF-child)` → `(ORG-…)` → `(control parent, control)` — the **first pair that actually sweeps ≥5 degrees** between rest and the sample, measured and then named in the report. Deform bones, not FK controls, because a Rigify limb can be posed in FK or solved in IK and only the bottom of that stack moves in both. The 0→1 ramp is **keyframe points on the driver F-curve** with `CONSTANT` extrapolation, never a Python expression: Blender gates expression drivers behind "Auto Run Python Scripts", and a rig that silently stops correcting itself on another machine is worse than none. Several samples get **triangular** ramps so the keys interpolate rather than stack.

**It verifies itself**: after authoring, the harness re-runs over exactly the joints and angles in play with the drivers live, and the before/after table is part of the result. Baseline is taken with every corrective **muted**, so "before" is linear-blend skinning rather than the last run. Measured on a synthetic two-bone limb (820 verts, one smooth blend band): knee.L **29.7% → 13.6%** at 90 degrees, **55.3% → 33.3%** at 120, **8.7% → −4.9%** at 60. Partial recovery, reported as partial: a convex hull is set by its outermost vertices and only the side that pinched is pushed (212 of 380 band vertices at 90 degrees — the outer side of a bend legitimately bulges), and `rig_check`'s hull metric is not a pure pinch measurement at extreme flex either, which is visible as the *negative* loss at 60.

**`rig_check` is evaluation-correct for this, and now says so.** It already measured the depsgraph-evaluated mesh, so shape keys and their drivers were always in the numbers; what changed is that each joint's region is built from those **evaluated** rest coordinates rather than raw `mesh.vertices` (additive `rest_world` argument to `JointProbe`), and the result carries a `shape_keys` block naming what was live. Proved the only way that counts: muting the corrective makes the harness's number worse again (13.6% → 29.7%). `animation_check` needed no change — it tracks bone positions through `scene.frame_set`, which evaluates drivers, and shape keys cannot move a bone.

**Export: glTF carries morph targets and has no concept of a driver.** Left alone, a corrected character reaches Godot with the morph present and pinned at weight 0 for ever, silently. `rigforge_export_godot` now bakes the second half: per clip, per frame, the driver is evaluated **through the depsgraph** (reading the original `key_blocks[...].value` returns the authored 0 at every frame) and keyed onto the export copy, whose inherited drivers are removed first because a driver beats a keyframe on the same property. The keys go into an action pushed onto an NLA track **named after the clip**, which is what makes Khronos' exporter merge them into the same glTF animation as the bones; interpolation is forced `LINEAR`, because a Bezier handle between two samples of a ramp overshoots past 1 and a morph weight above 1 inflates the limb. `export_morph`, `export_morph_animation`, `export_morph_reset_sk_data` are passed explicitly and asserted present on the installed 5.0.1 exporter. The exporter's own shape-key-driver path (`get_sk_drivers`, live in `NLA_TRACKS` mode) is deliberately **not** used: it samples whatever the original control rig happens to be posed at, and by export time the original holds one arbitrary action for every clip, so all of them would get the same weight curve. Round trip measured: the `.glb` carries `corr_knee_L_090` as a named morph target and a `weights` channel inside the bone clip running `0.00 … 0.96, 1.00` across a ten-frame bend. Result gains `morph_targets`, `driven_morph_targets`, `morph_animation`.

**The fix ladder, now law in `assistant/system_prompt.md`:** correctives first (quote before/after), weight painting second, **never a blind density pass** — and cite 50.3% → 51.1% when someone asks for one. Suite: `addon/tests/headless_correctives.py`, port 9908, 67 checks; `headless_rigik.py` (106), `headless_phase5.py` (150), `headless_phase4.py` (179), `headless_rigbridge.py` (108) and `headless_silhouette.py` (174) re-run green.

### The human rigger's workflow (2026-09-17, measured) — implemented

The owner's audit: *"you can clearly see that the bones is not aligned with the mesh… it doesnt seem symmetrical even. we shouldnt even be doing generation, we should replicate what a person does in blender to solve these problems that have already been solved."* Three defects were measured on the live character, and **no human using Blender's own tools could have produced any of them**:

1. **L/R bone asymmetry of 6-24 mm on every limb** (`DEF-foot` 23.5, shin 18.8, hand 17.1). An artist who places one side and presses `Armature ▸ Symmetrize` gets **0.0**.
2. **Bones off the limb's centreline**, visible in a render.
3. **Side names mirrored**: `DEF-shin.L` at `x = -191 mm` while the character's left leg centres at `x = +182 mm`. Automatic weights hid it — they bind by proximity, so the wrongly-named bone still drove the flesh beside it — while X-mirror tooling, retargeting and Godot's humanoid mapping all read the suffix and all break silently.

So `rigforge_metarig`'s **default path is now the workflow a rigger performs**, in order, with a number at each step (`addon/forge/tools/rigforge_landmarks.py`; the old tag-fraction fit remains as `method: "tags"` and as the automatic fallback, which says so). Three additive commands, no MCP mirrors (same `mcp/` lane as `rig_check`):

| type | params | result |
|---|---|---|
| `rigforge_landmarks` | `{"object"?, "action"?: "report"\|"prepare", "orient"?: "fix"\|"report"\|"strict"\|"skip", "symmetry"?: bool, "symmetry_keep"?, "symmetry_tolerance_mm"?, "stations"?}` — steps 1-3 alone; `report` changes nothing | `{"orientation", "symmetry", "symmetrized", "side_tags", "midplane_mm", "character_left", "landmarks": {role: {how, mm}}, "limbs", "says", "warnings"}` |
| `rigforge_echo_skeleton` | `{"rig"\|"metarig"?, "mesh"?, "dir", "views"?, "resolution"?, "deform_only"?}` — the skeleton over the ghosted body | `{"images": [{view, path, bytes}], "bones_drawn", "ghost_alpha", "says"}` |
| `rigforge_weight_maps` | `{"rig"?, "mesh"?, "dir", "bones"?, "views"?, "resolution"?, "max_bones"?, "overlap"?}` — per-bone weight maps + the overlap matrix | `{"images": [{bone, view, path, mass}], "ramp", "overlap", "says"}` |

**1. The orientation gate.** A body is lopsided front to back and symmetric side to side, so the horizontal axis whose **bottom and top slabs are lopsided** (toes, nose) is the facing axis and the other is left/right. Convention: **faces -Y, +X is the character's left**. Off-convention meshes are rotated a whole multiple of 90° and the rotation is applied; a mesh with no measurable front is **assumed** on-convention with a loud warning (refusing would block featureless characters that have nothing to fix), and `orient: "strict"` refuses instead. The mirror residual about both axes is measured as corroboration and **reported, never a veto** — a body whose asymmetry is concentrated in one limb can measure less symmetric about its real sagittal plane.

**2. Symmetrize first.** Two measurement decisions are load-bearing, both found by being wrong first: the residual is the distance from each mirrored point back to the **surface** (a BVH) rather than to the nearest vertex (a re-meshed half is not an asymmetric character); and the verdict is the **p95** while the **midplane search is scored on the mean** over a ±3% window. Scoring the search on p95 lets the plane park halfway into a shifted leg, where the leg scores zero and the torso is a minority of the vertices — measured, a **60 mm leg shift reported as 1.1 mm**. An **already-unwrapped** mesh is measured and left alone (symmetrizing would mirror half the UVs and orphan the bake); the rig is still mirrored and the warning quotes how far that leaves the right-side bones from the right-side flesh. `symmetry: false` fits each side to its own geometry — the artist's deliberately asymmetric character is legitimate, a generated accident is not, and only the artist can say which.

**3. Sides from geometry.** The tag at `x > 0` is the `.L` tag whatever it was called. Runs **before** symmetrize (which copies one half's groups onto the other and destroys the evidence) and again after.

**4. Landmarks, character-left only.** A limb is sliced perpendicular to its own centreline at 33 stations (second pass re-slices on the local tangent). Knee/elbow = **minimum-girth station in the 30-70% band**; ankle/wrist = the distal girth minimum; hip/shoulder = the junction where girth exceeds 1.6× the limb's median, with the hip pulled to the torso's own depth; spine/neck **on the midplane by construction**. Fallbacks are named in the report (`"how": "midpoint fallback"`), never dressed as measurements. The single most important line: a slab **widens until the slice has no angular gap over 120°** — a fixed thin slab lands between edge loops or clips one obliquely, and the centroid of half a ring sits well off the axis (**measured: landmarks 9.6 mm off a 16-sided arm's own centreline**, which is defect 2). Two safety gates fall back to the tag fit rather than lying: a principal axis more than 60° off the anatomical hint is the cloud's shape talking (a blob-stack leg measured a **horizontal thigh**), and three joints that do not march down the limb are not landmarks.

**4b. When the landmarks decline, the rest of the workflow still runs.** A tag that is a blob rather than a limb is refused *before* it becomes bones — its principal axis had to be replaced by the anatomical hint (a sphere-stack leg), or its crease is a midpoint fallback (nothing to measure that the tag fit does not already guess) — and the fit falls back to tag positions **but still orients, symmetrizes, re-derives the sides and mirrors** (`fit_method: "tags+mirror"`). Only the joints' *positions* come from fractions; the 0.0 mm two-sides guarantee does not depend on them. This matters because the acceptance test is the difference between a stable pipeline and a coin flip: Quadriflow's retopo is not deterministic, a marginal blob was passing on some runs and failing on others, and the run where it passed left a leg whose IK pole moved the knee **0.02 mm**.

**5. X-mirror.** `Armature ▸ Symmetrize` written out: reflect head/tail, negate roll, parents before children, snap unsided bones onto the plane, match sides on whole name **components** so `brow.B.L.001` is not mistaken for a centre bone. Asymmetry is **0.0 by construction** and a test pins it there.

**6. The echo-back, before skinning.** Red prisms per deform bone over the body ghosted to 22%, front and side, composited in `bpy` (transparent film is premultiplied, so the ghost is an add, not a lerp). Never fatal — a render that cannot run costs a warning, not the metarig.

**The same math inverted is the self-check, and `rig_check` reports it on every call** (owner: *"can the system not determine that the bones are not aligned where they should be?"*): `centering` (mesh **edges sliced at the plane** — collecting nearby vertices instead reported a perfectly placed thigh as **334% off centre** off a 3-vertex "section"; the shaft is gated, the head and tail reported, and only the four long bones are judged because a foot correctly runs along the top of its flesh), `asymmetry` (about the rig's **own** midplane: a character modelled 40 mm off the origin is not asymmetric), `side_naming` (the live 373 mm swap, which fails loudly), and `overlap` — the **influence overlap matrix**: per bone pair, shared `vertices`, `mass = Σ min(w_a, w_b)` in vertex units, `share_pct` of the smaller bone, `gap_mm` between the segments and `hops` through the tree. Touching bones are the blend band; a pair sharing influence across a gap is a named defect. The **geometric gap** decides rather than the tree, because Rigify re-parents `DEF-` bones into their own hierarchy and some are disconnected entirely.

**A price, measured and paid knowingly:** the IK pole bend was lowered from 3% to 0.5% of limb length to flatter the centering gate, and `headless_rigik`'s pole test caught it — **0.02 mm** of knee travel over a 25% pole sweep, because Rigify derives a limb's pole angle from its *rest* plane. It went back to 3%, and the centering band (a third of the section radius, heuristic tier) is what absorbs it.

**`joints_file` selects the tag fit**, and the result says which fit ran. A detector's predictions are a refinement *of tag-derived landmarks* — blended in, overruled by them — while the landmark workflow takes every joint off the mesh's own cross-sections and authors one side; both cannot be in charge, and silently ignoring a file someone produced on a GPU is the worse resolution. `method: "landmarks"` passed explicitly wins and says the file was read and not used.

### Auto-tagging from detected joints (2026-09-18, measured) — implemented

The landmark rigger above is only ever as good as its **limb tags**, and that turned out to be the binding constraint. Measured on the werewolf: the `Arm.L` tag was an axis-aligned **box band** — everything outboard of a fixed `x` above a fixed `z` — and on a figure whose arms hang at its sides that band is a wedge of shoulder, deltoid and rib, 219 mm wide and 636 mm tall, whose principal axis points **down the body** rather than down the arm. The landmark fitter refused it, correctly (*"the tag 'Arm.L' is not shaped like a limb"*), fell back to `tags+mirror`, and `rig_check` reported 3 centering failures and 12 overlap strays including *"96 vertices are moved by both `DEF-shin.R` and `DEF-spine`, two bones 360 mm apart"*. A box has three directions and they are the world's; a limb has one and it is its own. **UniRig detects joints; joints define axes.**

Two additive pieces, `addon/forge/tools/rigforge_autotag.py` and `rigbridge/detector_runner.py`, plus one new parameter on `rigforge_metarig`.

| type | params | result |
|---|---|---|
| `rigforge_autotag` | `{"object"?, "action"?: "report"\|"apply", "source"?: "auto"\|"detector"\|"box", "joints_file"?, "radius_factor"?: 1.6, "seed"?, "refresh"?, "replace"?, "rigbridge"?, "timeout"?}` | `{"tags": {tag: {vertices, source, why}}, "sources", "axes", "axis_hints", "roles", "girth", "sub_tags", "detector", "says", "warnings"}` |

**The tag math.** The detected tree is cut into **segments** (maximal single-child runs between the root, the branch points and the leaves — on a biped, exactly one per part). Segments are named from **geometry, never from the detector's names** (UniRig emits `bone_0`…, read as no name at all): the chain leaving the root upwards nearest the midplane is the spine, the one above it the neck/head, the longest sided chain ending in the bottom 40% that side's leg, the longest remaining sided chain starting above the waist that side's arm. Each limb axis is that polyline with the **branch point dropped** (it sits on the midplane; an axis starting there runs through the torso — measured: a leg tag reaching 1125 mm up a 1879 mm figure, taking the whole pelvis), continued through its longest descendant twig so the hand rides the arm's axis, and grown at its far end by however far its own flesh overshoots it. Then **every vertex joins the nearest axis** — distance to the polyline, which already partitions along the body rather than along the world — and each limb caps its claim at `radius_factor` × its **own local girth**, the median radial distance of its own vertices at 17 stations, re-measured after every reassignment. A vertex beyond the cap is the rib the arm hangs beside; it is offered to an axis whose own girth accepts it, and keeps the nearest when none does. Torso and head are the uncapped residual, so every vertex lands in exactly one tag.

Two wrong turns, both kept in the tests. *"Rejected, so give it to the torso"* put the **soles of the feet** in the torso tag (a Torso from 7 mm to 1420 mm) — a heel a metre from the spine has no better owner, so rejection now requires an acceptor. And **scoring every axis in units of its own girth**, which is the more elegant rule, runs away: the residual cannot reject, so its claim grows, so its girth grows, so it claims more — on the werewolf, 1279 → 4678 vertices, taking most of both legs. Nearest-axis stays in millimetres; girth is a cap, not a scale.

**The T-pose assumption was half the bug.** `biped_landmarks` assumed an arm runs sideways and a leg runs down, so a *perfect* cylindrical tag around a hanging arm was still refused — its principal axis is 60°+ from `+X`, the limb replaces its axis with the hint, and `_limb_is_measurable` then refuses it for having needed to. The tag was right and the hint was wrong. `biped_landmarks` gained an additive `axis_hints` parameter (default: exactly the old behaviour) feeding both the slicing axis and the plausibility gate; hints are stored on the object stamped with the bbox they were measured on, so a moved or rebuilt mesh is never fitted to a stale one.

**Credibility is per limb, and named.** UniRig's F1 ≈ 0.105 cross-domain, so each limb is checked against the mesh it claims — long enough for the figure, enough vertices to cross-section, thinner than it is long, and its tag's own principal axis within the same 60° the fitter will apply. A limb that fails falls back alone, and every tag reports its rung: `unirig` (a cylinder on its own detected axis) → `hand` (the tag already there) → `box` (this module's own band — the method whose failure is the reason it exists).

**`tags: "auto"` is a repair, not a rewrite**, and this is the load-bearing default. It does not re-tag every mesh that meets a GPU: the landmark fit is attempted first, and a mesh it can read keeps every tag it has. Only a **refusal** triggers a detection, and the rebuild must then earn its place — the fit is retried, and if it still refuses the original tags are **restored exactly** and the run says the repair did not take. Auto-tagging can therefore only move a mesh from *refused* to *fitted*, never sideways. Not theoretical: on the Phase 3 blob sculpt the detector's tags left the fit still refusing and moved `thigh.L`'s head from 726 mm to 252 mm — worse, and more expensive. An untagged mesh keeps its existing "tag it first" refusal and costs no detection; `tags: "detector"` is the explicit way to tag from scratch and refuses rather than falling back.

**The runner** (`rigbridge/detector_runner.py`) is the long-queued wrapper, and it is **stdlib-only by contract**: it imports nothing from UniRig, spawns `detect_joints.py` under UniRig's own virtualenv with `CREATE_NO_WINDOW`, and reads a JSON file — so the GPL boundary is a process boundary that cannot decay into a library import. It **never raises**: a closed set of reasons (`disabled`, `runner_missing`, `unirig_missing`, `python_missing`, `weights_missing`, `gpu_unavailable`, `mesh_missing`, `mesh_unsupported`, `busy`, `timeout`, `detector_failed`, `bad_output`) each cost the calling command a fallback, not a traceback. One job at a time behind an expiring lock file (inference peaks ~8.5 GB of a 12 GB card). A **cache keyed on the mesh's own SHA-256** plus every argument that changes the answer plus the checkpoint's identity, so re-tagging is free and provably the same mesh. One frame trap closed at the producer: the add-on exports with the **world transform baked in and an identity object matrix**, so the frame the detector calls `mesh_local` *is* world — the werewolf's object sits 933 mm up, and without this every joint would have failed the frame gate.

| gated centering failures | 3 (`shin.R.001` 78.8%, `upper_arm.L.001` 68.9%, `forearm.R.001` 65.7%) | 2 (`forearm.R.001`, `forearm.R`) |

The stray mass collapsed **143×** and the fallback is gone. With `symmetry: false` both arm failures disappear (`forearm.R` 72.3% → 51.4%, `forearm.R.001` 89.1% → 31.5% ok) at the cost of the 0.0 mm mirror — so the residual is the unwrapped asymmetric mesh, not the tags. One honest wrinkle: `forearm.R.001` improved at every station in **millimetres** (86 → 51 mm at 35%) while its **percentage** worsened, because the section it is judged against shrank from 130 mm to 74 mm — the bone moved out of a slice of body and into the forearm, and the proxy metric is a ratio.

### Tag-constrained skinning (2026-09-18, measured) — implemented

Auto-tagging computes an **exact per-limb vertex membership**. Until now the skinning step threw it away and let Blender's bone heat decide, and on the symmetric werewolf (`projects/werewolf/models/werewolf-wip-8.blend`, 8218-vertex retopo) the owner spotted what that costs by looking at the weight maps: **`DEF-upper_arm.L`'s heat sat on the chest and the torso's side, not on the arm** — the arm's swing visibly dragged the torso in the walk — and **`DEF-thigh.L`'s map was patchy**, islands of weight with punctures between them inside the one limb.

Neither is a bug in bone heat. Heat is a diffusion solve **over a connected surface**, and on a clothed figure whose arms hang down, the surface path from the deltoid to the rib is a couple of centimetres — shorter than the path down the arm. Heat therefore flows across the armpit faster than it flows down the limb. It is answering a question about the surface; the rigger was asking a question about the **body**, and the tags already know the answer. (Corollary, checked in the suite: a figure built as *separate* tubes cannot reproduce the bleed at all, because there is no surface to diffuse over. The bleed is a property of a welded retopo.)

One additive module, `addon/forge/tools/rigforge_skin.py`, one new stage at the end of `rigforge_generate_rig` (`tag_constrained`, default on), one new gate on `rig_check`, and one command.

| type | params | result |
|---|---|---|
| `rigforge_skin` | `{"object"?, "rig"?, "action"?: "apply"\|"report"\|"continuity"\|"isolation", "max_influences"?: 4, "blend"?: 1.0, "reach"?: 3.0, "smooth_passes"?: 4, "smooth_factor"?: 0.5, "split"?: true, "swing_deg"?: 30.0}` | `{"weight_removed", "weight_removed_pct", "borrowed_slots", "taper_slots", "out_of_reach_vertices", "worst_bones", "tags", "blend": {seams, refused_seams, girths_mm}, "sub_tags", "contract": {legal, legal_merged, spans, hinges, source_counts}, "continuity", "continuity_articulated", "isolation", "report", "says", "warnings"}` |

**The contract, derived from the metarig's own tree — never a list.** Ownership has three rungs and the report names the rung each bone stopped on: the stored `forge_tag_bones` mapping (`mapping`); then the **nearest ancestor with a tag** (`hierarchy`); then the nearest measured tag region (`geometry`). Then one asymmetric rule turns ownership into legality: **a tag may be moved by the bone it hangs *from*, never by the bones that hang *off* it.** `Arm.L` gets the arm chain plus `DEF-shoulder.L`; `Leg.L` gets the leg chain plus `DEF-spine`, the hips; `Torso` gets the spine, the breasts, the pelvis bones and the shoulders and **not** `DEF-upper_arm.L`. That refusal is the cure. On the werewolf all 35 deform bones resolve from `mapping` (29) and `hierarchy` (6) — `geometry` never runs.

Two traps, both closed and both in the tests. **Rigify's generated hierarchy is not a tree**: it re-parents every `DEF-` bone under its own `MCH-` scaffolding, and walking it found a deforming ancestor for exactly *one bone in thirty-five* on the live rig — so the parent link is read from the metarig, which the artist and this add-on both built, and only falls back to the generated rig when there is no metarig. **And `.NNN` is ambiguous**: Rigify subdivides `upper_arm.L` into `DEF-upper_arm.L` + `DEF-upper_arm.L.001`, but its human metarig *also* names bones `spine.001`…`spine.006`, so the naive "strip the digits" rule turns `DEF-spine.006` — the head — into `spine`, the hips. It did exactly that: both legs were handed the head bone as their hip hinge and the stray mass went up eightfold. The metarig's own bone table decides.

**Blend zones, in the limb's own units.** A seam is an edge whose ends carry different tags; from every seam the band is walked out over the mesh's own edges to `BLEND_GIRTH_FRACTION` (1.0) × the girth of the **thinner** tag there, and inside it both tags' bones are legal. From that one constant the werewolf's arm/torso seam comes out 68 mm and its wrist seam 22 mm, because an arm and a wrist are not the same thickness.

**Reach, and what it is *not* for.** A borrowed bone must also be within `BLEND_REACH` (3.0) × the lending tag's girth, fading over the last 35% rather than ending, because a hard distance threshold is a wall and a wall in a weight map is a crease. A tag's **own chain is exempt** — a knee is a long way from the top of its own thigh — and that exemption was measured, not assumed: applying the reach to a tag's own bones scaled the thigh down at the knee, sharpened the bend into a fold, and gave the werewolf's knees **474 new self-intersections where they had none**.

**Smoothing repairs, it does not blur.** Laplacian passes over the *weights* (the smoother `silhouette._smooth_field` runs over a displacement field and `correctives` runs over a correction — one implementation, three fields), but stencilled to two kinds of cell: a **hole**, filled back up to the level of the neighbours that carry weight, and a **mask rim**, faded towards its whole neighbourhood including the zeros. Everything else keeps bone heat's own answer, because bone heat's answer *along* a limb is good — it is only *across* limb boundaries that it is wrong, and the mask has already dealt with that. Blurring the healthy middle of a limb costs real deformation: on the synthetic test biped, four unrestricted passes mixed `DEF-thigh.L` into `DEF-shin.L.001` and the stray mass went from 8.9 to 34.1.

**Measured, headless, on the real character** (`werewolf-wip-8.blend`, nothing written back into it — verification output goes to a scratch copy):

| | before (bone heat as bound) | after (tag-constrained) |
|---|---|---|
| overlap stray mass | **fail** — 4.351, 3 pairs (worst: `DEF-hand.R` + `DEF-shin.R`, 503 mm apart, 23 vertices) | **ok** — **0.000, no pairs at all** |
| in-limb continuity (new gate) | attention — 417 punctured vertices, 1.71% | attention — **313**, 1.35% |
| `DEF-upper_arm.L` — region / holes | 1233 verts, 13 holes | **918 verts** (the chest is gone), **8** |
| `DEF-thigh.L` — holes | 15 | **11** |
| new self-intersections at the extremes, summed | 950 (elbow L 354, chest 366, shoulder L 230) | **2** |
| bone centering | **fail**, worst 58.2 mm off | **attention**, worst 36.0 mm |

5.7% of the skin's weight sat outside its own tag and was removed; the stage costs **0.4 s** on 8218 vertices.

**Two numbers that need reading carefully, said out loud rather than buried.** First, **the volume-loss percentages are not comparable before and after**, because the hull each is measured over changed: `rig_check` picks the vertices a joint's bones move, and before the fix `DEF-forearm.R`'s vertices included a slab of rib — the elbow's rest cross-section was **43 803 mm²**, a section 236 mm across, which is not an elbow. Afterwards it is **11 464 mm²**, which is a werewolf's forearm, and a real forearm loses more of its own volume at a 120° bend than a forearm-plus-chest does. Where the hull is unchanged the comparison is clean and it is favourable: knee R 38.2% → 27.8% and head 6.0% → 4.2%, both on a byte-identical section area. Second, `rest_intersections` went **2428 → 3164**. That is not the mesh at rest: this rig has **nine posed bones and 353 mm of displacement saved in the file**, and `rig_check` measures its "rest" after forcing IK→FK, so the number is a property of that saved pose and does depend on the weights. A control run (`rig_check` twice, nothing changed in between) reproduces 2428 exactly, so the move is real — and it sits against the 950 → 2 on the extreme poses the harness actually drives.

**The gate this adds.** `rig_check` grows a fifth placement gate, `continuity`: per bone, how many vertices *inside* its own region are punctured — at least 3 neighbours the bone moves above 0.05, own weight under half their mean, and an absolute drop of at least 0.15 so a legitimate falloff at a region's rim is not counted. Overlap catches flesh shared *between* bones; nothing caught flesh missing *from* one, which is what a patchy automatic bind looks like and what no existing number moved for. Bands (heuristic, proxy tier): ok ≤ 0.5% of the bone's region, attention ≤ 3%.

### The anatomical pre-bend and the bend-direction gate (2026-09-18, measured) — implemented

The owner watched the `werewolf-wip-9` walk and saw the **knees bending backwards**. Every existing gate was clean — the bones were inside the flesh, the two sides matched to 0.0 mm, the side names were right, the influence matrix was tidy and the foot slide was 1.1 mm. A rig can be perfectly placed, perfectly mirrored and perfectly planted and still fold the wrong way, because not one of those numbers is about *what happens when an animator pulls on it*.

**The root cause is one word in one function, and it is a lesson about measurement.** `rigforge_rig._bend` asked *how far from straight* a limb's three points were, and left the chain alone above 3% of its span. A magnitude cannot tell a knee from a knee bent backwards. Measured on the live rig: `knee.L` sat **25.9 mm behind** the hip-to-ankle line — **4.2%** of a 620 mm span, comfortably past the test — and `elbow.L`'s 31.6 mm off-line was almost entirely *sideways*, **0.08 mm** of it front-to-back. Both passed. Lifting `foot_ik.L` a quarter of the leg's chord drove the knee **148.7 mm backwards**, and Rigify — which derives a limb's pole angle from its **rest plane** — had put `thigh_ik_target.L` **625 mm behind** the chain, where it held the knee there through every solve.

**The missed human practice is the fix.** A rigger pre-bends: a slight forward knee and a slight backward elbow in the rest pose, always, before anything is animated, so the solver never has to guess. Three additive pieces, all in the existing lane.

**1. The pre-bend, in the landmarks** (`rigforge_landmarks.prebend_joint`, run inside `biped_landmarks` between the joints landing and the mirror). The offset is measured **signed, along the direction the joint is supposed to apex** — forward for a knee, backward for an elbow, both relative to the facing the orientation gate measured, never a hard-coded axis. Three outcomes: already apexing the right way by at least the minimum, **untouched** with the measurement that earned it; collinear or short, topped up; bent the **wrong** way, pushed through zero, which costs more than the bend itself (the werewolf's knee moved **43.7 mm** to reach +18.6 mm). The nudge **cannot leave the flesh**: `Limb.section_reach` measures how far the limb's own cross-section extends in the push direction at that station — the same ring-and-gap gates `bone_centering` applies before it trusts a section's centre — and the nudge is capped at two thirds of it, with the clamp reported. And it runs **before the mirror**, so both sides get it identically and the 0.0 mm asymmetry survives (pinned at 1e-6 mm by a test). `_bend` itself is fixed the same way and stays as the backstop for a chain the landmarks could not nudge; it now takes the facing from the landmark pass rather than a constant, so the two cannot disagree.

**2. Pole-side verification** (`rigforge_rig.pole_side_check`, reported by `rigforge_generate_rig` and `rigforge_ik` as `pole_sides`). Per limb, the pole's perpendicular offset from the chain against the anatomical direction. **There is nothing to fix on the generated rig** — moving the pole bone would leave the IK constraint's `pole_angle` aimed where the bone used to be, which is worse than the fault — so a wrong pole is a `fail` whose sentence says exactly that and names the pre-bend as the fix. Forward comes from `rig_forward_axis`: **ankle to toe tip**, the same rule `rigforge_walk` derives its forward axis from, so a gate and the walk it protects cannot disagree about which way is forward.

**3. The sixth placement gate** (`rigcheck.bend_direction`), and it is the only one that **drives** the rig rather than measuring it at rest. Per IK limb: switch to IK with the pole live, zero the pose (so the answer is a property of the rig, not of the pose the file was saved in), translate the IK target **a quarter of the limb's own rest chord towards the limb's root** — for a leg that is lifting the foot, the owner's own test — and project the mid joint's travel onto the direction it should apex. Then put it back and check it is back (`returned_mm` under 0.1 mm; the whole pose restored in a `finally`). The floor is **15% of the lift**, a heuristic with daylight either side: a straight two-segment chord that shortens by `d` must swing its mid joint `0.5·√(d(2L−d))` — 205 mm on this leg — so a correct rig clears it by an order of magnitude and an ambiguous one cannot reach it by accident.

**How big should the pre-bend be? Swept and measured, on the real character**, regenerating the rig at each step (`werewolf-wip-9`, 8405-vertex retopo, scratch copy — nothing written back; the sweep was taken with the pre-bend as the only variable, before the foot fit below moved the ankle, so the absolute travels are a little smaller than the final table above):

| pre-bend, % of the limb's span | knee travel, 155 mm foot lift | elbow travel, 152 mm hand lift | `bend_direction` | worst gated centering |
|---|---|---|---|---|
| 0.0% | **−0.0 mm** | −0.0 mm | fail | attention, 52.5% |
| 0.5% | 70.0 mm | 13.5 mm (under the floor) | fail | attention, 55.8% |
| 1.5% | 132.5 mm | 38.8 mm | ok | fail, 65.4% |
| **3.0%** (shipped) | **148.8 mm** | **68.9 mm** | **ok** | fail, 80.3% |

The first row is the argument: a perfectly straight limb's joint travels **zero** in either direction. It is not nearly right, it is undefined. 3% is the number `LANDMARK_BEND` already carried, and this project has been wrong about it once before — it was lowered to 0.5% to flatter the centering gate, `headless_rigik`'s pole test measured **0.02 mm** of knee travel over a 25% pole sweep, and it went back.

**The price, paid knowingly and quoted rather than tuned away.** A pre-bent joint is a joint off its own cross-section's centreline, and moving a bone's head tilts its whole shaft. `bone_centering`'s own threshold note already predicted the size of it — "29% of the forearm's radius on the test character" — and it cost **28 points** on `DEF-forearm.L`. It crosses from `attention` into `fail` *on this character* because that forearm starts at 52.5%: the mesh is 21.3 mm out of X-symmetry and deliberately not symmetrized (it is already unwrapped), so the rig is authored on the left and mirrored onto a right side 21 mm away — the residual the auto-tagging entry already measured and explained.

### The foot, the hand, and two bones nobody wanted (2026-09-18, measured) — implemented

Three more defects the owner found by **looking at the rest pose**, all of them the same shape as the one above: a part of the skeleton nothing measured, left wherever Rigify's template happened to put it.

**1. The foot did not follow the shoe.** `biped_landmarks` stopped at the ankle. `foot`/`toe` were never fitted at all — `fit_chain` placed `thigh` and `shin` and `_drag_subtree` **dragged the foot along** by whatever the shin's tail moved, so its proportions were the template's. Measured on `werewolf-wip-9`: `DEF-toe.L`'s tail ended **80.1 mm short of the boot's forward extent**, and the ankle sat **73 mm too high**. A foot roll that pivots inside the shoe rolls the shoe.

So the foot is measured **in its own frame**, because it is not the shape the rest of this module slices: a limb is a tube sliced across its axis, and a foot is a wedge lying on the ground whose joints are defined along the way the character *faces*.

| landmark | the rule |
|---|---|
| **ankle** | the height, between the ground and 45% of the way to the knee, where the leg is **shortest front to back** — a foot is long and an ankle is not, so the collapse of that length *is* the joint. The **lowest** station within 5% of the minimum wins, which is "just above the foot mass" rather than "somewhere up the shin" |
| **ball** | where the sole's **forward taper begins**: cut the sole into 17 stations, take the widest, walk forward to the first under 85% of it. A bootmaker's definition, and it works on a bare foot and on a boot |
| **toe tip** | the sole's own forward extent, **12 mm back** from the last vertex, so the bone does not break the surface the instant the toe rolls. The margin is quoted, not hidden |
| **heel** | the sole's rearmost cross-section **at ground level**, spanning the sole's measured width — which is what Rigify's `heel.02` becomes (`foot_heel_ik`), and therefore where a heel strike pivots |

All three bone positions are **cross-section centroids** like every other landmark here, so a foot bone runs through the middle of the toes rather than along the top of the sole. Applied before the mirror; the chain is now `thigh → shin → foot → toe` in one `fit_chain` call.

**It declines rather than inventing a boot.** A leg tagged to the ankle gets no foot landmarks and a warning saying so. Two guards, and the second was found by being wrong first: the foot must be 1.35× longer front-to-back than the ankle above it, **and it must point forward** — the sole must reach 1.6× further in front of the ankle than behind it. Length alone let a bare leg's end cap, which flares to 1.5× the ankle's width, read as a **126 mm foot**. A cone's cap is centred under the leg; a foot is not, and that asymmetry is the whole difference.

**2. The hand was the same defect at the other end.** On a clean rest-pose render the wrist sat **deep in the palm** and the hand bone reached the **fingertips**. `hand` was dragged exactly as `foot` was, and the wrist came from `girth_minimum(DISTAL_BAND)` — "the narrowest station in the distal band" — which walks straight past the palm, **because fingers are narrower than a wrist**. Two rules, both about where a girth profile turns:

- **the wrist** is the *first* local minimum walking distally — the forearm's taper bottoming out with the palm widening after it. Not the narrowest station, for the reason above;
- **the knuckle line** is where the palm tapers into fingers (the same 85% rule the ball uses), and the hand bone ends **there**, not at the fingertips, because that is where a hand hinges.

One more thing found by being wrong first: the search band is measured **from the elbow**, not from the middle of the whole limb. The elbow is itself a girth minimum, and a band starting at mid-limb found the elbow's own crease and called it the wrist — which on the synthetic biped made the arm's IK bend backwards, caught by the gate above. On a mitten-shaped synthetic hand the rules land **5.3 mm** from the wrist ring and **26.2 mm** from the knuckle ring the builder made.

**It declines on the werewolf, and that is the honest answer**: its `Arm.L` tag's girth is flat at 31–45 mm for the whole 249 mm past the elbow — there is **no palm in the tag**. The run says so and names the remedy, which is a tagging job, not a fitting one.

**3. Two bones nobody wanted.** Rigify's human template carries `breast.L/R`. On a jacketed male they show as prongs off the chest in the skeleton echo, and they are not innocent: measured on the werewolf they were in **33 of the overlap gate's stray pairs**, including **129.8** units of mass shared between the two of them and **78.4** between `DEF-breast.L` and `DEF-upper_arm.L`. `rigforge_metarig` grows `breast_bones` (default **false**) and drops them **on the metarig, before generation** — the only place it costs nothing, because a bone deleted there never becomes a `DEF-` bone, a vertex group or a weight map, whereas deleting the generated bone afterwards would leave both behind. `dropped_bones` reports it. The werewolf goes 35 → 33 deform bones with no breast vertex groups; a control run with them kept measures the **same 6 unweighted vertices** and the same unused bones less those two, so the skinning is unaffected.

**And the echo now has joints in it.** The owner's note on the first skeleton echo they looked at: *"I couldn't see where the bones articulate."* A chain of prisms drawn end to end is one continuous red worm, and the question that picture exists to answer — *does the knee sit where the flesh creases* — is a question about the **hinge**. `_bone_sticks` now welds a ball at every distinct bone head and tail (35 on the werewolf, sized off each bone's own prism so a finger's joints stay finger-sized), and `render_skeleton_echo` reports `joints_marked`. `joint_markers: false` gets the stick-only picture back.

### Sub-tag skinning: the arm swing that tugged the thighs (2026-09-18, measured) — implemented

The owner, on the wip-9 walk: **arm swings visibly tug the thighs**. Every gate said the skin was fine — `influence_overlap`'s cross-tag stray mass was the thing the last lane drove to 0.000 — and the gates were not lying, they were answering a question nobody had asked. Overlap names bones in *different* tags sharing flesh; continuity counts holes. What the owner saw is neither: it is a **displacement**, and nothing measured one.

**So the first thing built was the measurement.** `rigforge_skin` grows `action: "isolation"` (`arm_swing_isolation`): the arm chains and their hinges are swung 30° about the character's own lateral axis, mirrored L/R the way a walk does, and the mean and maximum movement of the **pelvis-tagged** and **thigh-tagged** vertices is reported in millimetres — near zero passes, bands ok ≤ 1 mm / attention ≤ 5 mm (heuristic, proxy tier). The question is about the *weights*, so the deform bones are driven directly with their rig-side constraints muted (Rigify's `COPY_TRANSFORMS` would otherwise overwrite every rotation and the measurement would be of nothing) and the baseline is captured in that same state; every pose bone's `matrix_basis` and every constraint's `mute` is snapshotted, restored, and the restoration **verified** — `restored_max_mm` is 0.0004 mm on the werewolf, a float round trip. One qualifier was measured rather than assumed: the thigh group is thigh-**tagged**, not merely thigh-weighted. The werewolf's hanging hand sits beside its thigh and twelve `Arm.R` vertices carry 0.17 of `DEF-thigh.R.001` across the blend band; counting those made the worst vertex a *hand* vertex moving 648 mm, which is a hand doing what a hand does.

Measured first, then fixed — and **the measurement contradicted the predicted mechanism**, which is the whole reason for taking it. The prediction was that the single `Torso` tag (thirteen deform bones in one legal set) let shoulder and breast weights sit on pelvis flesh, which then blends into the thighs. On wip-9 the pelvis slab moves **0.000 mm** under an arm swing: that path carries no weight at all. The 396.8 mm the thighs *do* move is `DEF-hand.R` and `DEF-forearm.R.001` on **leg-tagged flesh**, via a blend band nobody should have opened.

**Two tags touching is not two tags articulating** (`articulations`, `articulated_edges`). A blend band exists so a *joint* does not crease; `blend_zones` opened one at every seam, and on a figure whose arms hang at its sides the hand touches the thigh. It is the same error bone heat makes at the armpit — spatial adjacency read as anatomical connection — one level up. The contract already knows the difference: a tag's **hinge** is the bone it hangs from, and the tag owning that bone is the one it articulates with. `Arm.R` and `Leg.R` share no bone, so no band. On the werewolf that refuses eight seams (`Arm.R`/`Leg.R` 55 seam vertices, `Arm.L`/`Head` 78, `Leg.L`/`Torso.abdomen` 87, …). The **edge graph** everything walks is cut there too, and both halves of that cost a run: leaving the *taper* across a refused seam put the hand's weight straight back on the thigh through the smoother's hole filler (353 → **545 mm**, worse than before), and leaving the *Laplacian* across it eroded every rim weight a little more on each `apply`, so the stage stopped converging.

**The `Torso` split was still worth building, and the overlap matrix says why.** It is a derived view, never a tag: `rigforge_autotag.spine_split` cuts the torso into `Torso.pelvis` / `Torso.abdomen` / `Torso.chest` on the same 17-station grid the girth cap uses, and **nothing is written to the mesh** — no vertex group, no custom property — so `measure_tags`, the landmark fitter and the metarig keep seeing exactly one `Torso`, and a mesh re-tagged by hand can never be skinned against a stale split. Cut 1 is the p95 of the leg tags' own position along the spine (not the max: a limb tag's topmost vertices are the ragged seam it shares with the torso, and on the werewolf p95 and max are 68 mm apart — the hip against the belly). Cut 2 is the narrowest station of the spine's own girth profile between the legs and the shoulders, accepted only as a strict local minimum at least 2% below its band's mean; a uniform trunk has no waist and falls back to the midpoint, saying so. On the werewolf both rules land on station 10, which is the corroboration. A vertex is a point and lands in one slab; **a bone is a span**, and a bone crossing a cut is legal on both — the blend zone's rule one level up — while the slab holding its midpoint stays its single owner so "hangs from" still means something. The flesh past the end of the chain belongs to the bone at that end (without which the synthetic biped's pelvis slab came out with an empty legal set, its `Torso` tag running 80 mm below its lowest torso bone). A sibling seam's band is measured in **slab length**, not girth (0.25 — and 0.5 is the value that cannot work, because the two bands then meet in the middle and the slab has no interior of its own: measured 0.50 → 12.931 stray/366 holes, 0.35 → 3.806/377, **0.25 → 0.586/395**, 0.10 → 0.100/415).

**The continuity rise is the fix, said out loud rather than buried.** The gate counts a vertex with three or more weighted neighbours and none of its own as a puncture. **A limb is a tube until its extremity, where it is a hand** (`DISTAL_STATIONS`, `DISTAL_PERCENTILE`). The girth cap's median is right along a shaft, where the contamination is flesh the axis over-reached into and sits far out. At the tip there is no rib: a hand is a ball the axis runs *into*, and a median of its cross-section is dragged down by the flesh near the axis. Measured on the werewolf's `Arm.L`, the profile fell monotonically to **28.8 mm** at its last station while the palm reaches **75 mm** from the hand bone — a 46 mm cap around a 75 mm palm, with a 79 mm-girth thigh hanging beside it ready to accept what the arm threw out. ### Tangents and the Godot LOD convention (2026-09-13, research-verified) — implemented

- **Tangents are exported.** Khronos' exporter defaults `export_tangents` to **False**, so every asset shipped tangent-less and every engine regenerated the basis its own way — which is not the basis the normal map was baked against. Silent visual wrongness, never an error. `rigforge_export_godot` now passes `export_tangents=True`, `export_normals=True` (the exporter ANDs the two: `gltf_tangents = export_tangents and export_normals`), `export_texcoords=True`, `export_materials="EXPORT"`, `export_image_format="AUTO"`. Verified against the installed Blender 5.0.1 `io_scene_gltf2` RNA; all five kwargs exist, and `op_kwargs` still filters by RNA so a future rename degrades instead of raising. Result gains `tangents: true`. The only other `export_scene.gltf` call in the add-on is `addon/tests/headless_meshgen.py`'s `write_glb`, which mints a **test input fixture**, not a shipped asset — left as is, deliberately.
- **`-lodN` is not a Godot import suffix.** Godot 4's list is `-col`/`-colonly`/`-convcol`/`-convcolonly`/`-occ`/`-navmesh` etc.; it generates LODs on import with meshoptimizer. So **`lods` is now a mode, not a bool**: `"auto"` (default) exports only the unwrapped LOD0 and lets Godot's importer do the levels, naming the siblings it left out in a warning; `"manual"` exports them under **their own object names** (no fake `-lodN` rename) and emits a `LOD_CHAIN` in `<name>_import.gd` that sets `visibility_range_begin` / `visibility_range_end` on each sibling — without which a manual chain renders every level at once. Bands are contiguous and strictly increasing, LOD0 begins at 0, the last level ends at 0 (Godot's "for ever"); distances come from each LOD's stored `forge_lod.visibility_begin`, or are measured at export time when absent. Result gains `lods` (the mode) and `lod_chain` (`[{mesh, begin, end}]`). Legacy `lods: true`/`false` still parse, as `manual`/`auto`.

## Phase 6 sketch — Forge Assistant (AI chat inside Blender)

Product philosophy — THE governing contract for the assistant, from the user verbatim in intent: **abstract difficulty away; enable the artist without them being an expert on the tech or Blender.** Concretely, every assistant reply follows one of three shapes:

This is the vendor echo-back pattern (the control surface teaches itself by arriving filled in) applied to a settings file.

**Contract.** `projects/<slug>/design/task-config.json`:

```
{"version": 1, "task": "character"|"part"|"device"|"floorplan"|"mold", "project": "<slug>",
 "settings": {"<name>": {"value", "default", "unit"?, "choices"?, "min"?, "max"?, "why"?}},
 "history":  [{"date", "setting", "from", "to"} | {"date", "note"}]}
```

**Templates** (`mcp/forge_mcp/task_config.py`, one table per task, data-driven — a new task is one entry):

| task | settings, with defaults |
|---|---|
| `character` | **`symmetry` true** ("bipeds are symmetric unless you say otherwise"), `target_engine` godot, `poly_budget_desktop` 15000 tri, `lod_chain` auto, `texture_res` 2048, `rig` biped_ik, `correctives` true, `face_detail_pass` false |
| `part` | `printer_profile` (`templates/printer.json`), `wall_mm` 2.0, `bed_fit` `design_full_size`, `export_formats` `["stl"]` |

| `floorplan` | **generated from `service.floorplan.DEFAULTS`** — ceiling 2400, wall 100, door 820×2040, window 1200×1200, sill 900, label height 850, floor 50, label anchor |

- **Values SETTLE AT READ TIME.** `task_config.setting(project, name, fallback)` is the consumer API and it goes to disk on every call — no cache, and never a value a model passed in from memory. An edit made in a text editor is a supported way to change a setting and is tested as one. **The first real consumer is `floorplan_validate`**: `task_config.plan_defaults(project)` fills the plan's `defaults` block with anything the plan itself does not state, so precedence is **plan → sheet → the service's own `DEFAULTS`** (a number typed into *this* plan is a decision about this plan and always wins), and the report names which numbers came off the sheet. A project with no sheet, or one scoped to another task, validates exactly as before.
- **Defaults are mirrored, never retyped.** A ceiling height that is 2400 in the sheet and 2700 in `build_floorplan` is a level built at a height nobody typed, so the floor-plan block is *generated from* the builder's own table and the maker choices come off the catalog, through the same lazy-and-guarded `service/` import every other coupled module uses. Written-down fallbacks exist for a checkout with no `service/`, and a test compares them to the real ones so they cannot drift.
- **It is not a second writer.** The sheet goes through `save_design_doc`'s `design_paths` + `normalize_design_content`, so one set of slug/traversal/JSON checks guards `projects/<slug>/design/`.
- **`task-config.json` is deliberately NOT in `DESIGN_READING_ORDER`** — that tuple is a *reading* order and is mirrored byte for byte in `assistant/bridge.py`; the settings file files alphabetically exactly as `floorplan.json` does.
- **MCP: 86 tools** (was 83). `task_config_init(project, task, force=false)` materialises and refuses to overwrite without `force` (naming what would be lost and pointing at `task_config_set`); `task_config_get(project)` echoes **every** value with the non-defaults marked; `task_config_set(project, name, value)` validates against choices/range/type and refuses in a sentence leaving the sheet untouched. `save_design_doc`'s report now names the sheet, or says how to make one.
- **Prompt:** `## Design before geometry` gains deliverable **0** (materialise the sheet *before* the questions, so fewer are needed), the law *"settings come from the sheet — change the SETTING and say so, never carry a value the sheet owns in conversation memory"*, and the symmetric-bipeds law verbatim in spirit. `## Rigging and animation` opens by reading the sheet for the budgets it passes to retopo/rig/export.
- **Web UI: READ-ONLY, and the reason is in the code.** `GET /library` puts a design file's name, size and path on a card and **never its contents**, and the bridge has **no write route onto `projects/<slug>/design/`** at all. A key/value form would therefore be drawn over values the page has not got, with a Save button pointing at a route that does not exist. The card instead gets a `lib-config` panel naming the sheet, saying the assistant owns it, and two buttons that prefill the composer ("Show the settings" / "Change a setting") — the one path that actually validates the value and writes it. Making it editable needs a bridge route, which was out of this lane.
- **Tests:** `mcp/tests/test_task_config.py` — **84** tests (template completeness per task, the two mirror checks against `service/`, init/get/set round-trip, the echo report marking non-defaults, settle-at-read including an out-of-band edit, the `floorplan_validate` consumer and its precedence, and the refusal set) inside a **1205-test** MCP suite (was 1121); `assistant/tests/test_webui.py` gained 2 (the card panel, and the read-only verdict asserted as *no request and no form* rather than as a comment).

#### The staged build pipeline — `design/build-plan.json` (2026-09-19) — implemented

Owner directive, near-verbatim: *character (and similar) builds are a **staged pipeline the artist drives step by step** — "make the mesh", "check it", "now rig it" — **never an assumed one-shot**. Each stage ends with its gate verdict and its artifacts; a red gate blocks the next stage.*

This is mechanism **1** of the queued *guaranteed-better runs* section below ("process gates move from prose into code"), built as a state machine rather than as prose. Without a file that says what stage a build is at, the stages live in the conversation, which means they live nowhere: the next turn re-rolls the whole build, a failed gate is stepped over because nothing remembers it was red, and *"what state is this character in"* has no answer but scrollback.

**Contract.** `projects/<slug>/design/build-plan.json`, **extended additively** over the shape real plans already carry — the werewolf's is the live example and it predates every key below:

```
{"version": 1, "project": "<slug>", "task": "character"|"part"|"device"|"floorplan"|"mold",
 "notes": ..., "components": [...],          <- whatever was already there, untouched
 "stages": [{"id", "title", "status": "pending"|"in_progress"|"passed"|"failed"|"overridden",
             "gate": [check names], "artifacts": [paths], "numbers": {name: value},
             "history": [...], "does", "tools": [tool names]}],
 "history": [{"date", "note"}]}
```

**Chains** (`mcp/forge_mcp/pipeline.py`, one table per task, data-driven exactly as `task_config.TEMPLATES` is — a new task is one entry in each):

| task | stages | example gates |
|---|---|---|
| `character` | reference → design → generate → clean *(symmetrize/retopo/bake/unwrap)* → verify_mesh → rig → skin → correctives → animate → export | `symmetry_residual_mm`, `rig_check.centering`, `rig_check.overlap`, `rig_check.volume`, `animation_check.foot_slide_mm`, `morph_targets` |
| `part` | design → author → generate → check → export | `params_parse`, `bed_fit`, `min_wall`, `overhangs`, `watertight` |
| `device` | design → circuit → author → generate → check → export | `voltage_v`, `resistor_ohm`, `components_fit` + the part gates |
| `floorplan` | extract → validate → echo → build → reconcile | `rooms`/`openings`/`fixtures`, `plan_reads_clean`, `sign_off`, `objects_built`, `drift` |
| `mold` | design → source → undercut → mold → export | `undercut_verdict`, `parting_z_mm`, `halves_watertight`, `draft_deg` |

Every gate names a measurement Forge can actually make — the character chain's are `rig_check`'s and `animation_check`'s own field names — because a gate naming a check nobody can run is a gate nobody can close.

- **MCP: 89 tools** (was 86). `pipeline_status(project)` renders the board (marker column: `[x]` passed, `[!]` failed, `[>]` in progress, `[ ]` pending, `[~]` overridden) with every stage's verdict, numbers and artifact paths, and ends naming **next** as the exact call to make. `pipeline_advance(project, stage, override?, who?, why?)` starts ONE stage. `pipeline_record(project, stage, status, numbers?, artifacts?, replace?)` is how a build turn writes its result in.
- **They are the state machine and nothing else.** No function in `pipeline.py` runs Blender, generates a mesh or measures anything; the assistant does the work *between* the stages. A test drives all three against dead backend ports to pin it.
- **The plan settles at read time**, exactly as `task_config` does: every call goes to disk, nothing caches, and an edit made in a text editor is a supported way to move a stage.
- **Which stages exist comes from the project's task** — the plan's own, else `design/task-config.json`'s. Precedence is **plan → sheet**, the same shape `floorplan_validate` uses. A project with neither is a refusal naming `task_config_init`, never a guessed chain: inventing the chain would invent the gates that block the build.
- **A red gate really blocks.** `pipeline_advance` over a failed stage is refused in a sentence naming it *and quoting what it measured*; over an unfinished one, refused as a skip. `override=true` goes on anyway and requires **`who` and `why`** — the stepped-over stage is then marked `overridden`, **never `passed`**, and *both* stages carry the signature in their history for good. An override with no name and no reason is refused: three sessions later is exactly when that matters. `pipeline.blocked(project)` is the consumer API for anything that must refuse to present a build over a red gate.
- **A stage cannot pass with nothing measured.** A green verdict with no number beside it is an opinion, and the next stage has to be able to read what this one got; the refusal names that stage's own gate and offers `{"sign_off": true}` for the stages that really are the artist's yes. Numbers and artifacts **merge** across calls (a stage is usually measured by more than one tool) unless `replace=true`. Recorded paths are checked against disk and the board marks any that are not there — a path is a claim.
- **It is not a second writer.** The plan goes through `save_design_doc`'s `design_paths` + `normalize_design_content`, so one set of slug/traversal/JSON checks guards `projects/<slug>/design/`. Broken JSON is a refusal that leaves the file exactly as it was and is **never** rebuilt from the template behind anyone's back: this file records what has already been built.
- **The werewolf's plan migrates by gaining keys and losing none.** It has `notes`, eight `components` carrying nested measurement blocks, and no `task` and no `stages`. `load` materialises the ten-stage character chain *in memory* beside them; the first write adds `task`, `stages` and `history` and touches nothing else (verified: `components` and `notes` byte-identical after a round trip). `version` stays **1** — a version-1 reader that knows nothing about stages still reads every plan correctly, which is what additive means. The board prints the components as a separate line ("what the build is MADE of, beside the stages, which are how it gets made"), because they are a different axis and folding one into the other would lose both.
- **`build-plan.json` is deliberately NOT in `DESIGN_READING_ORDER`**, for the same reason `task-config.json` is not: that tuple is a *reading* order mirrored byte for byte in `assistant/bridge.py`, and this is the machine's record of what was built. It files alphabetically.
- **Visibility:** every report that already named the settings sheet now also names the board — `save_design_doc`, `task_config_init`/`get`/`set`, `floorplan_validate` — through the same caller-supplies-a-line pattern (`pipeline.mention(slug)`, beside `task_config.mention(slug)`), so no formatter grows an import it does not need. The server's `INSTRUCTIONS` carry the directive verbatim: *do one stage, record its verdict and its files, show the artist, and let THEM say go on.*
- **Tests:** `mcp/tests/test_pipeline.py` — **51** tests (chain completeness per task, status round-trip through disk, settle-at-read including an out-of-band edit, advance refusing over red while quoting its number, advance refusing a skip, the signed override on both stages, board rendering naming numbers and artifact paths and marking a path that is not on disk, the four `next:` shapes, the visibility wiring on all four reports, and a werewolf-shaped plan loading, rendering, driving and round-tripping without loss) inside a **1257-test** MCP suite (was 1206). `test_server_tools.py`'s count pin moves 86 → 89.

### Phase 19 sketch — floor plans to prototype levels (draw rooms, get walls)

User intent (2026-09-09/12, near-verbatim): "I draw rooms, walls, doors, and give it a label key — washer/dryer here — and I want a simple 3d level created with the walls and doors, and washer/dryer as rectangles to help map out. Then from there we can edit a shape and make it more complex. We should be able to do prototypes; on the floor plans and basic 3d rooms we should allow modifications on drawings without full regen; we support additions."

**The contract is a typed plan file, and the plan file is the model.** No generative 3D anywhere in this phase — it is the parametric lane end to end, and the drawing's meaning lives in `projects/<slug>/design/floorplan.json`:

```
{"version": 1, "units": "mm", "scale": {"mm_per_px"?, "calibrated_by"?},
 "defaults": {"ceiling_mm": 2400, "wall_mm": 100, "door_w_mm": 820, "door_h_mm": 2040},
 "rooms":   [{"id": "room-kitchen", "label"?, "polygon_mm": [[x,y],...]}],
 "walls":   [{"id": "wall-01", "from_mm": [x,y], "to_mm": [x,y], "thickness_mm"?, "height_mm"?,
              "openings": [{"id": "door-01", "kind": "door"|"window"|"gap", "at_mm": <along wall>,
                            "width_mm"?, "height_mm"?, "sill_mm"?, "swing"?: "in"|"out"|null}]}],
 "labels":  [{"id": "wd-01", "label": "washer/dryer", "footprint_mm": [x,y,w,d], "height_mm"?,
              "rotation_deg"?, "source": "user"|"library"}],
 "history": [{"rev", "date", "note"}]}
```

- **Stable ids are the incremental-regen law.** Every room/wall/opening/label carries an id that survives edits, and the id names the Blender object (`FP:wall-01`, `FP:wd-01`). Rebuilding is a DIFF against ids: an edited entry rebuilds only its own objects, an added entry only creates, a removed entry only deletes its own — **never a full regen**, so hand edits to untouched components survive by construction. A component the artist has manually edited (mesh differs from what its plan entry would build) is SKIPPED on rebuild with a warning naming it, never clobbered — promotion (making a shape more complex) is one-way, and the plan keeps the slot's footprint as the size contract.
- **Extraction is two layers, per the thesis.** Deterministic first: threshold/line extraction off the drawing, wobbly hand lines snapped straight and to right angles where within tolerance (the verify.py mask machinery is the seed). VLM assigns semantics only — which gap is a doorway, what each key label means — over the computed segments, never inventing walls. Scale is calibrated by ONE user-stated dimension (`scale_mm_per_pixel`, exactly fit_to_silhouette's), asked in the design phase.
- **Echo-back approval before any 3D.** The assistant renders its READING back as `design/floorplan.svg` — rooms colored, doors with swing arcs, labeled footprints with intended real sizes — and the user corrects the diagram, not the mesh. Mandatory gate, the design-phase sign-off applied to a scene.
- **Geometry is extrusion + booleans, per component.** Walls extrude centerlines to height, openings are booleans, each room may get a floor slab; labels become named box components at real-world default sizes (an appliance/furniture dims library with sane measured defaults — washer ≈ 600×600×850 mm — same provenance spirit as components.py). Doors may carry Phase 17 `mechanism` records (revolute about the hinge edge, `range_deg: 90`) so demos and the robotics/game exit come free.
- **Promotion, not regeneration (the follow-up ask).** Every placeholder is a component SLOT: elaborate it parametrically, swap in a generated/imported mesh that inherits the slot's exact footprint and placement, or hand-sculpt (+ fit_to_silhouette against a photo). The level never rebuilds around a promotion.
- **Verification is the shipped machinery:** top-down orthographic render of the built level vs the plan's own rasterised mask, silhouette IoU (measured tier), per component and whole-plan.
- **Exits:** .glb greybox level for Godot (walls carry collision-ready geometry, labels are placeholder props); 3D-print miniature at bed-fit scale ("prints as N pieces" informational); walkthrough render.
- **Split:** service owns the plan contract, validation, diff and the appliance-dims library (`service/floorplan.py`); the addon owns `build_floorplan` (materialise/diff-update scene objects by id, bpy, undo-pushed); assistant/MCP round teaches the flow + echo-back SVG and mirrors the tools.
- **The service half — BUILT (2026-09-12, `service/floorplan.py` + `service/appliance_dims.py`, `service/tests/test_floorplan.py` — 164 tests).** Six entry points, pure stdlib + numpy, nothing imports build123d or bpy and nothing touches disk. `validate_plan(plan)` → a normalised copy (floats, stripped ids, `defaults` completed); `fill_defaults(plan)` → every optional number resolved; `diff_plans(old, new)` → exactly `{added, removed, changed, unchanged}` of ids; `component_build_specs(plan)` → ordered pure-data specs (walls, then floor slabs, then fixtures); `snap_segments(segments, mm_per_px?, tolerance_deg?, merge_mm?, angles_deg?, min_length_mm?, join_collinear?)` → `{segments, report}`; `plan_mask(plan, cell_mm?, bounds_mm?, pad_mm?, include_openings?)` → a numpy bool grid with its own transform, plus `mask_iou` and `plan_bounds`. **`DEFAULTS` is the add-on's `PLAN_DEFAULTS` key for key and a test pins it**, because the resolved plan this half produces is exactly what `build_floorplan` eats and a default the service spelled differently is one the add-on silently substitutes its own for; the add-on's two open-convention rulings (`at_mm` is the opening's CENTRE with `start_mm` the near edge and both-at-once refused; `footprint_mm` `[x, y]` is the box's CENTRE unless `anchor`/`defaults.label_anchor` says `corner`) are implemented here as the same rule, and so are its refusals — duplicate ids across all four entry kinds, overlapping openings on one wall, an opening past its wall's end or taller than it, a zero-length wall, a room with <3 corners or no area, non-mm units, an id too long to name a Blender object. **Refusals are sentences naming the entry** (`"room 'room-bowtie' crosses itself: the wall from corner 0 to 1 meets the wall from corner 2 to 3"`), and a missing id is refused rather than generated — an invented id changes next run and takes the artist's hand edits with it, so the refusal is the feature. Crossing is checked BEFORE area because a bow-tie has zero signed area and "encloses nothing" is the true but useless diagnosis of it; polygons normalise to an open counter-clockwise ring so two artists drawing one room in opposite directions diff equal. **The diff compares RESOLVED values and provenance lives in one top-level `provenance` map, never on the entries** — the add-on fingerprints each entry's canonical JSON, so a note saying *where* a number came from would make a wall look changed when only the bookkeeping moved; raising `defaults.ceiling_mm` therefore marks every wall that was taking its height from the block and leaves a wall with its own explicit height alone, dropping an explicit `thickness_mm: 100` when the default is already 100 marks nothing, an opening's change is also its wall's change (both walls when a door moves between them), and an id lands in exactly one of the four lists — a new wall full of new doors is `added`, never also `changed`. Unknown keys on an entry are kept verbatim and reach the build spec (that is how a door's Phase 17 `mechanism` record rides along) and they take part in the diff; unknown keys inside `defaults` are the one refusal, because a mistyped `ceiling_mm` is the typo that silently builds a whole level at the wrong height. Cutouts resolve to absolute boxes (centre, size, angle, four corners, jambs and the hinge jamb per `hinge`), grown 1 mm through the wall each side so the boolean never meets a coincident face — `joints.OVERSHOOT_MM`'s reason and number; walls sharing a corner each grow half a thickness into it and free ends do not, so corners come out square without sticking out past the drawing. `snap_segments` is the deterministic half of extraction: angle-snap about each midpoint, weld endpoint coordinates on capped-width 1-D clusters (single-link chaining would collapse a run of walls 100 mm apart), join collinear runs, drop tick marks — a 2-degree-wobbly 4x3 m rectangle comes out four axis-aligned segments closing on four corners, and the report names every id it moved and by how much. `plan_mask` rasterises **walls and fixtures but not floor slabs** (a slab fills a room, and an IoU against a filled rectangle measures the rectangle), and an opening cuts the mask only when it runs floor to ceiling — from above, a doorway with a header over it is still a solid wall, and pretending otherwise would make every correctly built level score badly; `mask_iou` refuses two masks on different grids rather than returning a number that means nothing and gets believed. `appliance_dims` is 30 entries with a one-line note saying what each number *is* ("US standard 27 in washer: 32 in deep, 38 in tall to the lid"); `lookup` has five routes in — canonical, alias, punctuation-squashed, token-subset (longest first, so "stacked washer/dryer" lands on the stacked entry rather than the pair it contains), then `difflib` above 0.72 — each reporting its own `how` and `confidence`, and an unrecognised label is `None` rather than a guess, which is the right answer because the caller then uses the footprint the artist drew. **The table never overrides a footprint**: a plan is top-down and has no height in it, so only the height comes from the library, and a fixture drawn more than 50 mm off its real size keeps its size and gets a note. **One divergence, stated rather than hidden:** a per-room `"floor": false` is honoured in the build specs and the mask but the add-on's `floor` is a whole-build toggle, so today it would still get a slab. **NOT done here: the MCP mirror, the assistant round and the echo-back SVG** — `mcp/` and `assistant/` belong to other agents, and no existing service file was touched (no HTTP route yet).
- **The add-on half — BUILT (2026-09-12, `addon/forge/tools/floorplan.py`, `addon/tests/headless_floorplan.py` port 9905, 208 checks).** Socket command `build_floorplan` `{"plan": <the floorplan.json object, resolved values, mm>, "collection"?: "Floorplan", "mode"?: "update"(default)|"rebuild", "floor"?: true}` → `{"collection", "built", "updated", "deleted", "unchanged", "kept": [{"id", "object", "why"}], "objects", "object_names", "walls", "openings", "fixtures", "floors", "rooms", "pieces", "mechanisms": [...], "bounds_mm": {"min","max","size"}, "dimensions_mm", "mode", "floor", "defaults_mm", "plan_version", "units", "honesty", "notes", "warnings", "seconds"}`. **Not read-only** (the registry pushes `Forge: build_floorplan`), a legal flow step, stdlib + bpy, no network, no service dependency — the plan arrives as data and the add-on does no image parsing and no validation the plan has not already had. **The incremental law is implemented as a fingerprint diff and asserted on allocation identity, not on the report:** a content hash of each entry's fully resolved values (canonical JSON + a `BUILD_VERSION`, so key order is not a change and a geometry-code change is) is written to `obj["forge_fp_hash"]` with `forge_fp_id`/`forge_fp_kind`/`forge_fp_verts`/`forge_fp_dims_mm` beside it; an unchanged entry's code path is a `continue` (same object, same mesh datablock, same materials, same transform, proven with `as_pointer()`), a changed one swaps only its own mesh datablock, a new id creates, a missing id deletes — and only ever an `FP:`-prefixed object *inside the named collection*. Defaults are resolved INTO each entry before hashing, so raising `defaults.ceiling_mm` rebuilds every wall and leaves the slabs and fixtures untouched. **Never clobber, and it applies to deletion too:** `forge_fp_keep=True` is an unconditional hands-off (honoured even in `mode:"rebuild"` — an explicit marker outranks a mode), as are a changed vertex count, dimensions off by more than 0.5 mm (which is what catches a viewport scale) and an `FP:` object with no fingerprint at all; each is reported under `kept` with a sentence and a warning naming the object, and an entry Forge kept is never counted as built/updated/deleted. Placement is deliberately NOT part of the heuristic: the plan owns where a placeholder stands, the artist owns what shape it is. **Openings are cut by construction, not by a Boolean** — a wall is the solid pieces left over (full-height pier between openings, sill under a window, header over anything short of the ceiling), which is exact, has no solver to time out and is fast enough to rebuild per keystroke; a `gap` runs floor to ceiling and splits its wall into two disjoint piers. Rooms get an optional slab hanging below z = 0 (tessellated, so an L is an L); labels are boxes at footprint + height + `rotation_deg`. Three shared flat materials by kind (`Forge FP Wall`/`Floor`/`Fixture`), `diffuse_color` set as well as the Principled base because a greybox lives in Workbench. **Two conventions the schema left open, decided in the add-on and documented:** an opening's `at_mm` is its CENTRE along the wall from the `from_mm` end (additive `start_mm` gives the near edge; both at once is refused), and a label's `footprint_mm` `[x, y, w, d]` puts `[x, y]` at the box's CENTRE (`anchor: "corner"` or `defaults.label_anchor` switches it). Additive fallback defaults the schema does not spell, all overridable via `defaults`: `window_w_mm` 1200, `window_h_mm` 1200, `sill_mm` 900, `label_h_mm` 850, `floor_mm` 50. A swinging door returns a Phase 17 record `{joint_type: "revolute", axis: [0,0,1], origin_mm: <hinge edge on the centreline>, range_deg: 90, direction: ±1, swing, hinge, width_mm, height_mm, actuated_by}` — **data in the report only, no leaf object and no rigging**, and `direction` is the product of swing and hinge side. The whole plan is parsed before one thing in the scene is touched, and refusals are sentences: duplicate ids (ids name objects, so they are unique across rooms/walls/openings/labels), an opening wider than its wall, a label with no footprint, an unknown kind or mode (with `difflib` near misses), an opening off the end, overlapping openings, a zero-length wall, a room with <3 corners or no area, non-mm units, an id too long for a Blender name. ## Live context awareness — the copilot's eyes — implemented

User ask (verbatim, 2026-09-12): **"it should have live context awareness of blender otherwise its useless as a copilot."** Until this, the assistant saw Blender only at the moment it chose to call a tool — which means it saw the thing it asked about and nothing else. An artist who moved a wall, deleted a closet and dropped into sculpt mode between two messages was invisible, and a copilot that cannot see the controls move is a copilot in name only.

- **The add-on half — BUILT (2026-09-12, `addon/forge/tools/activity.py`, `addon/tests/headless_activity.py` port 9906, 116 checks).** New READ-ONLY socket command:

| type | params | result |
|---|---|---|
| `get_activity` | `{"since"?: epoch (Blender's own clock), "limit"?: int 1..200 (default 40)}` | `{"events": [{"t": epoch, "object": name, "kind": "transformed"\|"geometry"\|"added"\|"removed"\|"mode"\|"undo"\|"redo", "source": "artist"\|"forge", "count": int, "ago": seconds, "detail"?, "command"?}], "count", "matched", "truncated", "since", "now", "mode", "active", "selected", "selected_count", "cursor_mm", "collections_touched", "objects", "ring": {...}, "handlers", "watching", "kinds", "sources"}` |

  **One call answers "what has the artist done since I last looked"**, which is why the mode/active/selection/cursor ride along in it rather than needing a second `get_scene_info`. `get_scene_info` gained exactly one field — **`mode`** (Blender's own mode string) — and nothing else was reworked.

  A `@persistent` handler set on `depsgraph_update_post` + `undo_post` + `redo_post` + `load_post`, installed by `activity.register()` (last in `tools.register()`, first out) and **idempotent by marker attribute** rather than by identity, because an add-on reload builds new function objects and leaves the old ones in Blender's lists. **The classification is free**: every `DepsgraphUpdate` already carries `is_updated_geometry` / `is_updated_transform`, so the handler reads two booleans and a name off work Blender has already done — cheaper than the cached `(vert_count, matrix hash)` comparison the plan allowed for, and *more* accurate, since a vertex moved back where it started still sets the flag and a hash would call that nothing. **No mesh is ever read in a handler**, no `bpy.ops`, no context override, and shading-only updates are dropped (a material preview says nothing about the artist's work).

  **Bounded in every direction:** a 200-entry ring, ≤256 updates inspected per tick, an added/removed census that only runs when the object count changed *or* a name we have never seen appears in the updates (which catches a rename for the price of a set lookup) and is abandoned above 20 000 objects with the skip counted, and **coalescing** — same object, same kind, same source, within 2 s, folded into one event with a `count`. That last one is not a nicety: one drag fires hundreds of updates, and without it a single gesture would push everything else out of the ring. Measured: **0.13 ms per depsgraph flush**, and 120 flushes of a drag come out as one event.

  **Who did it is two mechanisms, because one is not enough.** `registry.dispatch` is wrapped (idempotently, restored on unregister, re-exported `forge.tools.dispatch` rebound with it) to keep a re-entrant depth counter — but Blender delivers `depsgraph_update_post` when the depsgraph is next *evaluated*, which for a command running in the socket pump's timer is normally **after** the command returned. So a **0.75 s grace window** opens on the way out, and without it every mesh Forge ever built would be reported as the artist's own work. The window is a judgement call and the honest one: the failure it can cause is an artist edit in the same fraction of a second as a Forge command being credited to Forge, and an artist is not dragging a vertex while they wait for an answer; the failure it prevents is the feed being wrong about *every* built object, every time. **A read command claims no credit at all** — `get_scene_info` calls `refresh_view_layer()`, which flushes whatever the ARTIST had pending, and if a read could take the credit then the more attentive the assistant was the blinder it would become. `CREDIT_READ_ONLY` is the two-name exception (`set_mode`, `sculpt_brush`: in `READ_ONLY_COMMANDS` for a reason about undo history, not a claim that they change nothing).

  **Handlers swallow and count, never raise.** A handler that throws is a handler Blender *removes*, which would turn one bad frame into a permanently dead feed; every body is wrapped, the failure count and last message come back in `ring`. `get_activity` joins `READ_ONLY_COMMANDS` (asserted, and asserted again by measuring that three calls leave object/mesh datablock pointers, transforms, selection, mode and cursor bit-identical). Timestamps are stored **unrounded** and rounded only on the way out, and `now` is floored to the millisecond — a rounded `t` compared against an unrounded clock comes out negative by half a millisecond and coalesced two ticks in three (measured: 120 flushes became 40 events); a `now` rounded *up* would be a bookmark that skips the half-millisecond of work it claims to cover.

- **The bridge half — BUILT (2026-09-12, `assistant/bridge.py`, `assistant/tests/test_webui.py` +22 tests → 363).** Every `/ask` turn — **and only `/ask`**, because the library, the workbench and the flow passthroughs are not conversations — opens with one socket call and injects one marked line into the prompt, between the panel's context block and the attachment (the attachment carries "Read this first" and has to be last on the page):

  `[Blender now] mode Object; active FP:wall-front-house; selected 1 (FP:wall-front-house); cursor_mm [0, 0, 0]; since your last look: artist moved FP:wall-x0-garage (2 min ago), artist deleted FP:closet-entry (5 min ago).`

  **Hard budget 600 characters**, newest first, older clauses dropped as `+N more` (with the room for that note reserved before the last clause is admitted, so a trimmed block never hides that it was trimmed). Verbs are the artist's words, not depsgraph flags (`transformed` → "moved"), a coalesced gesture reads `x340`, and `Forge edited Body` versus `artist moved FP:wall-01` is the distinction the whole `source` tag exists for. **The bookmark is BLENDER's own clock** (`now` from the previous call, kept per-conversation on `JobStore` and dropped with the session), so `since` filtering across two processes involves no clock-skew reasoning anywhere.

### Surface tuning — measured, not inherited (2026-09-13) — implemented

**`image_to_3d.json` is a converted ComfyUI *demo* template, and several of its surface settings are not the node's own defaults.** Inherited, never chosen: `RemeshMesh.smooth_iters` **20** (the node's MAXIMUM, against its own tooltip "2-3 cleans DC staircase-like artifacts; higher over-smooth QEF edges"), `sign_mode.qef` **false** (sharp-feature dual-vertex placement off — core defaults it true for `sdf`, false for `udf`, and the template runs `udf`), `project_back` **0** (nothing snapped back to the surface the model produced), both `MeshSmoothNormals.crease_angle` **180** ("no edge is ever hard"), structure sampler **12 steps / cfg 7.5**. So they were A/B'd on the GPU and the numbers written down.

- **The harness is `meshgen/tools/` and it is deterministic — geometry only, no VLM.** `ab_fixtures.py` synthesises the inputs (vectorised ray/solid cast over boxes and ellipsoids, so ground truth is exact and free) through **core's own camera rig**, imported from `make_rig_views.camera_basis` and extended by one elevation angle, with a test pinning the two identical at elevation 0. Three scenes: `hard_steps` (stepped ziggurat, creases at four scales — the sweep scene), `hard_slab` (the Phase 18(a) object, reused not retyped), `organic_blob` (four ellipsoids, the no-sharp-edges control). `mesh_metrics.py` scores silhouette IoU against the exact input mask, `edge_sharpness` (of edge length creased at all, the fraction still ≥60° rather than melted into a 5–60° ramp: a cube 1.0, a sphere 0.0, both pinned as tests), `crease_length`, `crease_normal_p95`, manifoldness, components, self-intersections (vertex-sharing pairs excluded, as `mesh_diagnose` does). `ab_tuning.py run|report` drives it, appends one JSONL row per run so an interrupted sweep resumes, and **exits 0 with a reason when meshgen/the weights/the GPU are absent** — the suite's contract.
- **Two measurement bugs found by building it, both silent:** (1) the exported glTF is **UV-split** (`UnwrapMesh` gives one vertex per position-per-island), so a closed mesh reports ~58 000 boundary edges and ~1 800 components, and — far worse — every crease a seam was routed along **drops out of the dihedral statistics**, which under-counts exactly the thing being measured; welding by position first moved the baseline's `edge_sharpness` from 0.006 to 0.061, a ten-fold difference. (2) A **zero-area face has no normal**, and dividing by its zero length hands it `(0,0,0)`, which scores a flawless 90° crease against anything — counting slivers as sharp edges would have put a floor under every variant. Mesh axes are the exporter's, so the silhouette is scored after a search over all 48 **signed axis permutations** (these come back Y-up, `[x, z, y]` with two flips) — a search over *labelling*, not a free rotation fit, and a test pins that a sphere cannot pass as a slab.
- **`edge_sharpness` alone is gameable and the harness says so.** Dual Contouring's voxel staircase is *perfectly* sharp and entirely fake, so a variant can buy sharpness by getting jaggier. `ab_fixtures.true_crease_length(scene)` computes the box scene's real total crease length (≤ **15.24** for `hard_steps`, counting buried edges, so the visible figure is lower) and measured excess over it is steps, not detail.
- **New OPTION_SPEC entries** (`backends/comfyui_base.py`), validated with ranges straight off core's node schemas and **refused, never clamped** — a node that silently clamps 500 iterations to 20 leaves the caller reasoning about a setting that never happened: `smooth_iters` (0–20), `qef` (bool → the DynamicCombo's namespaced `sign_mode.qef` key, not a nested object), `project_back` (0.0–1.0), `fix_poles` (bool), `crease_angle` (0–180). A spec's node id may now be a **tuple**: `crease_angle` is one artistic decision held by two `MeshSmoothNormals` nodes (one feeding the UV unwrap, one producing the exported normals) and setting only one gives a mesh whose atlas and shading disagree about where the creases are. Booleans use a **strict** coercer — `bool("false")` is `True`, and a JSON client that stringifies a flag must not silently turn sharp-feature placement on. `hard_surface` is a documented **macro, not a mode**: it pre-seeds the pair it is shorthand for, and an explicit option next to it still wins.
- **Measured, 19 GPU runs / ~55 min on the RTX 5070, one job at a time (full tables in meshgen/README.md).** Winners: **`smooth_iters` 20 → 3** (20 is the node's max; at 3 `edge_sharpness` 0.061 → 0.097 for no time or VRAM — and `smooth0`'s 0.147 is rejected as staircase at 2.1× true crease length) and **`qef` off → on** (sharpness +11%, shells 33 → 28, and `creaseL` stays *on* ground truth — it places the dual vertex rather than getting jaggier). **They compound far past their sum: together 0.281, 4.6× the template**, because QEF places the feature and low smoothing is what leaves it there. On `hard_slab` the pair lands on the analytic target exactly — `creaseL` **7.9 vs a computed 7.90** — where the template sits at **0.4**, 95% of the creases melted. On the organic control it costs nothing: identical IoU, self-intersections **5 → 1**, +1.5% time. Losers, kept on the record: **`project_back` stays 0** — 0.5 bought +0.0007 IoU for **70 self-intersections where there were none**, 1.0 bought +0.0016 for **13 391 across 465 shells** at 2.6× true crease length, both ~17% slower; it snaps DC vertices back onto the raw model surface, which is the mess the remesh exists to remove. **`steps`/`cfg` stay 12/7.5**: the checkpoint's 25/5.0 posts the sweep's best IoU (0.9801) and is 34 s faster while losing ~92% of crease length, and the full 2×2 shows the template's pairing is the **only** one of four that keeps creases at all (0.061/15.7 vs ≈0.005/≈1) — an interaction, not two knobs, with cfg 5.0 at 12 steps the worst silhouette measured. **Silhouette IoU moved only 0.976–0.980 across every variant** — a tuning table built on IoU alone would have shipped `project10`, the worst mesh in the set.
- **`crease_angle` stays 180 globally and moves to 45 only under `hard_surface`.** On hard surfaces 45 is close to free — geometry bit-identical by construction, crease-face shading error **164° → 13°** on `hard_steps` and **180° → 4.9°** on `hard_slab`, with slightly *fewer* exported vertices — but on the organic control it adds **4.8% more exported vertices** to split edges that should have stayed smooth and drives `normal_p50` down, which on a curved surface is faceting. **No metric in the harness scores that as bad, which is exactly why it is not defaulted**: `crease_normal_p95` is only a quality signal where the truth is "90 degrees", and a sphere *wants* its shading normals to deviate from its faces.
- **The chosen values live in `TUNED_DEFAULTS`, applied on top of the template exactly like `VRAM_SAFE_DEFAULTS`**, so re-running `tools/build_workflow.py` after a ComfyUI upgrade cannot silently restore the demo's numbers; `workflows/image_to_3d.json` carries the same values and a test pins the two together (and pins the derived `multiview_to_3d.json`, regenerated from it). **Negative prompts stay architecturally absent**: at the shape stage `negative` is the conditioning node's zero-tensor second output, so a `negative_prompt` option would be a control the caller could turn and watch do nothing — the most expensive kind of documentation lie. **meshgen tests: 153** (39 `test_service.py` + 53 `test_multiview.py` + **61 new `test_tuning.py`**), still runnable with none of the 23.8 GB present. The measured tables, the winners and the losers are in meshgen/README.md under "Tuning the surface: what was measured".

### Seed ensemble — deterministic verifier-pick over N draws (2026-09-13) — implemented

**The seed moves the mesh more than every setting in the tuning round put together, and meshgen was taking whatever the first draw gave.** Measured on `hard_slab`, five seeds produced five occupancy grids with pairwise IoU **0.53–0.72**, and two of the five disagreed with the input drawing at silhouette IoU **0.18 against the best draw's 0.80** — unsalvageable by any downstream knob. Research grounding: oracle best-of-5 is ~**26% Chamfer improvement** (arXiv 2604.27106); a symmetric-Chamfer **medoid** beat a VLM verifier on CAD with the benefit plateauing near N=9 (arXiv 2608.09706); ShapeGen's picker is geometric, front-view normals vs the input (arXiv 2511.20624). **Render-CLIP is chance and is named in the README only so nobody re-adds it.** No VLM, no CLIP, no eyeballing anywhere in this feature.

- **API: `options.ensemble {"structure_n": 1-9, "best_of": 1-5}`**, both defaulting to **1 (off)**, validated on `Backend` (so every adapter inherits it) and settled at **submit time** — a malformed block is a 400 before anything is queued, the same contract a bad `views` block gets. Refused, never clamped. Seeds are `seed, seed+1, …`, never random, so two runs of the same request compare the same candidates. **Both tiers above 1 at once is refused with the reason**: `best_of` already draws N independent structures, so consensus inside each would hand every candidate the same grid and charge N full generations for N copies of one mesh. `/job/<id>` carries the request block from queue time and **replaces it with the finished verdict** — seeds tried, every candidate's numbers, who was rejected and why, the pairwise agreement matrix, the winner, one sentence of `why`, `probe_ms` beside `wall_ms`.
- **The architectural fact that makes tier 1 possible:** the structure and shape stages meet at a **plain dense boolean occupancy grid** — `VaeDecodeStructureTrellis2` emits `[B,R,R,R]` (R 32/64), `Trellis2ShapeStage` consumes `torch.argwhere(...)`. Before that seam is seconds; after it (cascade, upsample, texture, remesh, unwrap, bake) is the 2–4 minute tail.
- **Split or fallback: NEITHER — a third route, and the reason matters.** The obvious design (capture the VOXEL, re-inject it into a second `/prompt`) **core cannot express**: exactly four node classes touch the `VOXEL` type and all four either produce or consume one — **no save node, no load node**, and writing one would be a custom node, which `custom_nodes/` staying empty forbids (the nvdiffrast/RMBG trap, standing law). But core has a lossless way **out**: `VoxelToMeshBasic` emits unit cube faces at **integer lattice points** and `SaveGLB` writes them through with no node matrix and no rotation (checked in core's `save_glb`), so the mesh *is* the grid. Hence the head is a **probe** and the winner is replayed as one ordinary full generation at the winning seed — one extra head execution, nothing core does not already ship, and **no fall back to full-pipeline best-of at low resolution was needed**.
- **The inverse is exact, not approximate, and two details carry it.** Interior voxels have no exposed face, so the face set alone under-reports a solid block — the solid is recovered by **parity along an axis** (faces perpendicular to it sit exactly at the solid/empty transitions). And the grid is computed independently from **all three axis families, which must agree**; they cannot unless the mesh really is a closed voxel boundary. That check is what keeps a silently wrong grid — and the plausible consensus table built on it — out of the report. Core's final `fliplr` is undone so the returned grid is indexed the way `VaeDecodeStructureTrellis2` indexed it.
- **Seed replay is deterministic, MEASURED not assumed:** three probes of seed 56 on `hard_steps` returned **4 752 occupied voxels each, pairwise IoU 1.000**. `ab_ensemble.py repeat` is the standing re-check after any ComfyUI or driver change; if it ever stops being 1.0 the structure tier is picking a seed whose grid it will not get back and the README must say so.
- **The probe graph is a PRUNING, not a second template** — reachability from the structure decode node over whichever graph the backend would have run (single-view *or* multi-view), plus a four-node tail. 55 nodes → **31**. A template refresh flows in automatically, so the two can never drift — a stronger guarantee than `multiview_to_3d.json`'s derived-and-compared one. Reachability is `build_workflow.py`'s rule and for the same reason: `PreviewImage`/`MaskPreview` are **pass-through data nodes** in this template, so pruning by "looks like a preview" guts the graph. Tail: `VoxelToMeshBasic → SaveGLB` for the grid, and `MaskToImage → ImageCropToMask → SaveImage` for the drawing — the mask goes through **the same crop node the model's input image did**, so the silhouette a grid is scored against is framed exactly the way the model framed the picture. (The crop composites `image × mask` on black and here the image *is* the mask, so the saved pixel is `mask²` and the 0.25 read-back threshold is `mask > 0.5`, not a guess.) `build_mask_graph` prunes further — background removal and a crop, **no sampler and no UNet at all** — which is how `best_of` gets its target silhouette for ~a second.
- **Tier 1 pick: silhouette gate FIRST, then medoid.** The gate runs before the consensus because two bad draws that agree with each other would otherwise outvote three good ones. Silhouettes are compared over the **24 axis-aligned labellings** (3 axes × 4 turns × 2 mirrors) — a search over *labelling*, not a free rotation fit, `mesh_metrics.best_orientation`'s discipline — and the labelling is chosen **once** and applied to every candidate, because candidates read different ways round are not comparable. The 0.15 margin is **relative and must be**: the camera behind a found image is unknown (photo = perspective at an arbitrary azimuth; grid = orthographic, axis-aligned), so the absolute number is not a quality score and is never treated as one. **The gate never leaves fewer than two survivors** — a gate that can empty the field decides the answer by itself. Then the medoid of the survivors' pairwise grid IoU; ties to higher silhouette, then lowest seed.
- **Tier 2 pick: hard gates, then rank.** Unreadable meshes dropped; topology gates on self-intersections and shell count **relative to the best in the batch** (3×, with a floor) — absolute gates are useless and this repo has the measurement that proves it, since a *good* run exports 9 boundary and 210 non-manifold edges, so "must be manifold" rejects everything every time. The limit is anchored on the batch minimum so the best candidate always survives; the gates may legitimately cut to one, and then the report says there was no consensus to take. Rank: silhouette IoU **rounded to 3 decimals**, then symmetric-Chamfer medoid (4 096 area-weighted surface points, fixed RNG seed — a quadrature rule, not a source of variation), then `edge_sharpness`, then seed. **The rounding is the measured part**: across the entire tuning sweep IoU moved only 0.9763 → 0.9801 while the meshes differed enormously, so it is a guard that the object was not eaten, not a quality ordering — rounding hands the decision to the consensus medoid wherever silhouettes are indistinguishable, which is nearly always. Every candidate mesh is **kept on disk** as `<name>_seed<N>.glb`; the caller paid for them.
- **A real bug fixed in passing:** `ComfyUIClient.run_graph` polled `/api/jobs/<the id we hold>` but accepted `prompt_id=None`, so a sub-run without one polled `/api/jobs/None` forever on a job that had already finished and failed on the timeout. It now mints a **canonical** uuid — ComfyUI v0.35 refuses anything else with `invalid_prompt_id`, which also rules out the obvious `f"{job_id}-structure-2"` naming for an ensemble's sub-runs. An ensemble submits several graphs per `/generate3d` job, so this went from corner case to ordinary.
- **`prepare_run` split into `stage_inputs` + `graph_for`** (Pixal3D overrides both, keeping the multi-view path intact) so an ensemble stages the image **once** and builds N graphs over it. Restaging per candidate would give every candidate a different `LoadImage` filename, miss ComfyUI's execution cache, and re-run background removal and the image encoder for every seed. With one staged name the probe costs **~6 s per distinct seed** (and ~1.5 s for a repeat of one already run — ComfyUI caches the whole identical graph).
- **Dependency boundary held:** meshgen's single-shot request path stays stdlib-only. `meshgen/ensemble.py` (numpy) and `tools/mesh_metrics.py` (numpy + PIL, both already in `service/.venv`) are imported **lazily**, only when an ensemble is requested, and a machine missing either gets a sentence rather than a single-seed mesh quietly pretending it was chosen.
- **Tests: 223** (was 153) — **70 new in `meshgen/tests/test_ensemble.py`**, all offline. Harness `tools/ab_ensemble.py repeat|run|report`, same contract as `ab_tuning.py` (real jobs through the live service, JSONL resume, **exit 0 with a reason** without GPU/weights).
- **MEASUREMENT IS PARTIAL AND SAYS SO — 3 of 9 planned rows; the sweep was stopped when the GPU was needed elsewhere.** What landed: seed replay deterministic (above); `hard_steps` baseline **0.9755 / sharp 0.284 / creaseL 57.9 / 177 s** vs `structure5` **0.9753 / 0.284 / 57.8 / 219 s picking seed 56** — i.e. the consensus kept the seed it started with, and the tiny deltas are the *tail's* own wobble, not the ensemble (selfX 0→3, shells 38→35 at identical face counts: **the structure stage is bit-deterministic at a fixed seed, the shape/texture/remesh tail is not quite**); `hard_slab` `structure5` **0.8866 / 0.167 / 8.3 / 105 s picking seed 58** with **2 of 5 draws rejected on silhouette (0.177 and 0.182 against 0.796)**. Cost is settled: **~6 s per distinct seed**, so `structure_n: 5` added **32 s to 177 s (+24%)** and **30 s to 75 s (+40%)**, VRAM unchanged. **Honest verdict: the tier is insurance, not an upgrade** — it cannot make the typical mesh better, only stop the atypical one shipping, and 2-in-5 unusable draws on `hard_slab` is the measured size of that risk. That is why both tiers default to 1. **Still unmeasured and NOT estimated:** `hard_slab` baseline (the missing half of the one comparison where the pick actually differed), **anything about `best_of` on real output** (it was seen submitting and running candidates and no further — its gates, Chamfer medoid and winner-copy are covered by offline tests against synthetic candidates only), and the whole `organic_blob` control. Resume with `ab_ensemble.py run --out <dir>`; it re-runs only what `results.jsonl` is missing. Full tables in meshgen/README.md under "Seed ensemble".

## PARAMS block convention (the PartForge script contract)

Every generated script is a plain Python file with, at top level:

```python
PARAMS = {
    "bowl_diameter": {"value": 152.4, "unit": "mm", "min": 50.0, "max": 300.0,
                       "step": 1.0, "description": "Outer diameter of the bowl"},
    "feet_count":    {"value": 4, "unit": "count", "min": 3, "max": 8, "step": 1,
                       "description": "Number of feet"},
}

def build(p):
    # p is a dict of param name -> resolved value (overrides applied, validated)
    # returns a Build123d Part / Solid / Compound
    ...
```

Rules: `value` AND `unit` required (`unit` one of `mm`, `in`, `deg`, `count`, `ratio`, `bool`); `min`/`max`/`step`/`description` optional but encouraged. Param names must be valid Python identifiers. Out-of-range overrides are rejected by the service (not clamped); `step` is a UI hint only. `in` values are converted to mm before `build()` is called (build works in mm). The service validates overrides against min/max and type. The Blender panel is generated from this schema verbatim.

## How an assistant turn ends (job states on the bridge)

`GET /job/<id>` reports one of **four terminal states**, and every poller must stop on all four:

| state | means |
| --- | --- |
| `done` | it answered |
| `error` | it could not |
| `cancelled` | the artist pressed Stop |
| `timeout` | it ran out of clock — **and here is how far it got** |

`timeout` is deliberately not `error`. The 2026-09-16 dogfood run (B-1) lost a fifteen-minute turn that had already written a 441-line `part.py`, generated it, taken a printability refusal from its own script, fixed it, re-checked and rendered it twice: the artist was shown one sentence saying it "was stopped", no reply, no cost, and the advice "try a smaller request". All four were wrong — the work was on disk, it had been explained, it had been paid for, and 595 of the 900 seconds had been a stall rather than work.

So the bridge accumulates the whole stream as it arrives (`ActivityRecorder`): every assistant **text block** in order, every tool call **with what it answered**, every path it touched, and any cost the stream volunteered. A turn that is killed lands all of it as `reply`, plus one honest closing line, plus `cost_usd` — a timed-out turn is folded into `session_cost_usd` exactly like a finished one.

Two clocks produce it, and they say different things because they are different diagnoses:

- `FORGE_ASSISTANT_TIMEOUT` (default 600 s) — the turn budget. Its message names the limit and *may* suggest a smaller request.
- `FORGE_ASSISTANT_STALL_TIMEOUT` (default 300 s, `0` disables) — how long the CLI may print **nothing at all** before it is treated as hung. Killed on this clock the job reports `"stalled": true` and `silent_for`, and the reply **never** blames the size of the ask: a hang would have swallowed a one-line request just as completely. It also leaves the rest of the budget unspent, instead of letting a dead process eat it.

The reply itself is **every** text block joined in order, not just the CLI's `result` string (which is only the model's last message). In a design tool the reasoning written *before* the tool calls is the product; the old one-block reply dropped it, and it survived only as clipped 60-character activity markers (friction F-1). The activity ticker stays what it is — a progress indicator that may be clipped mid-word — and the reply is never assembled out of it.

**Files on a job.** Paths are minted into `/file/<token>` tokens from tool arguments, tool results and the reply. Absolute paths are taken as written; **relative** ones (`prints/body.stl` — how a model naturally names a file it just wrote inside a project) are resolved against the working directory and the project folders, preferring a project the text itself names, and kept only if they exist on disk. `.stl` is servable as a download for the same reason: turns 8 and 11 of the dogfood run reported `files: []` while six finished STLs — the one thing the whole pipeline exists to produce — sat on disk unreachable.

## What is running (version truth on /health)

All three HTTP services — bridge (8901), geometry (8765), meshgen (8902) — carry the **same `build` block** on `GET /health`:

```json
"build": {"sha": "a1b2c3d", "pid": 12345, "started": "2026-09-15T18:22:04Z", "uptime_s": 913.4}
```

`sha` is `git rev-parse --short HEAD` for the working tree, **read once at process import**, never lazily: a checkout made after the process started must not let a stale process relabel itself as current, which is the entire point. No git, no repo, a timeout — all answer `"unknown"`, and startup never fails over it.

The **bridge additionally echoes `config`**: its *resolved* settings — `projects_dir`, `models_dirs`, `model`, `timeout_s`, `blender {host, port}`, `cwd`, `uploads_dir`, `previews_dir`, `thumbs_dir`, `services` — plus `env_set`, the **names only** of the `FORGE_*` variables set in its environment. Resolved, not raw: the raw string says nothing about what defaults, `abspath` and `meshgen/config.json` did to it. Names only for `env_set`, because `/health` is readable by the browser.

**One process per port (startup guard).** All three services allow address reuse, so a second start does not fail — it loses the port race and stays resident. The 2026-09-16 dogfood run found two of each alive on the machine, including a second meshgen holding a model loader on a 12 GB card (B-6). So each entry point now probes `http://127.0.0.1:<its port>/health` **before binding anything**; if a Forge service answers, it prints one line naming that process's `pid` and `sha` and **exits 0** — "already running" is the state the caller asked for, not a failure, and `start_forge.ps1` runs these on every launch. `FORGE_FORCE_START=1` skips the guard. An unreachable port is treated as free: a guard that refused to start on a bad probe would be worse than the duplicate it prevents.

The add-on's health row (`addon/forge/tools/services.py`) reads the checkout's HEAD **straight out of `.git`** — no subprocess, nothing inside Blender may flash a console — and folds a verdict into each of the three rows: the SHA appended to a fresh row's detail, and a **`STALE:` warning naming both SHAs plus `run stop_forge then start_forge`** when they differ. Three answers, not two: a service with no `build` block, a `"unknown"` SHA, or a zip install with no repo is *cannot tell*, never a verdict — an add-on that cried stale on every non-checkout machine would be ignored within a week. A stale required row turns the panel's summary line red even though every dot is otherwise green, because a service answering yesterday's code convincingly is worse than one that is simply down.
